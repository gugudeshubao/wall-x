# 第 1 篇草稿

## 标题

`别一上来就谈 CUDA：Wall-X 推理优化前，先搞清楚它到底是什么模型`

## 备选标题

- `Wall-X 到底是不是重度自定义算子模型？先别急着谈优化`
- `为什么 Wall-X 没有 MLA：从算子和结构先看清它的推理主干`

## 开头钩子

很多人第一次看 Wall-X 这类项目时，第一反应都是先找自定义 CUDA 算子，然后顺手给它贴一个标签：这是个深度魔改的推理项目。

这个判断并不准确。

Wall-X 除了 MoE 和 RoPE 相关算子，没有别的自定义算子，其他算子基本都还在 PyTorch 技术栈里。你如果要优化它的推理速度，先得搞清楚它的模型结构，然后才有优化空间。否则你看源码时很容易疑惑：为什么它没有 MLA，只有 MHA/GQA 和 FlashAttention。

这不是一个枝节问题，而是一个起点问题。因为你对模型结构的第一判断，会直接决定你后面优化的方向：你是会去盲目翻 CUDA kernel，还是先去识别真正的热点路径；你是会误以为它改了注意力数学本身，还是能看出来它的大部分复杂度其实在 MoE 路由、视觉 token 组织和动作生成链上。

所以这篇文章不先讲训练，也不先讲 flow action，更不先讲某个 kernel 的实现细节。先只回答一个最基础的问题：Wall-X 到底是什么模型，它的推理主干到底长什么样。

## 文章目标

这篇文章要完成 4 件事：

1. 先把 Wall-X 的自定义算子边界讲清楚。
2. 再把它的主干结构判断讲清楚。
3. 回答“为什么它没有 MLA”这个很容易冒出来的问题。
4. 给后面的推理优化分析建立一个正确的出发点。

## 详细提纲

### 1. 先别一上来就看 kernel，先看整体结构

这一节建议先写一个常见误区：

- 看到 `csrc/ops.cu`，就以为整个项目的核心都在自定义 CUDA
- 看到 `PYBIND11_MODULE`，就默认它一定改了整套推理栈
- 看到 MoE，就自动联想到“这个模型肯定魔改很重”

然后给出这篇文章的主判断：

- Wall-X 的确有自定义算子
- 但自定义算子的范围没有覆盖整个模型
- 主体结构仍然建立在 Qwen2.5-VL + PyTorch 常规算子链上

### 2. Wall-X 到底有哪些自定义算子

这一节可以把 `ops.cu` 暴露出来的接口按功能分三组：

- MoE 相关：`asym_dual_gmm`、`permute`、`unpermute`、`unpermute_bwd`
- RoPE / 位置编码相关：`rope`、`rope_bwd`、`rope_index`、`rot_pos_emb`
- 视觉分块相关：`get_window_index`

然后强调两个判断：

- 这些算子是“局部性能关键路径下沉”，不是整套模型重新实现
- 如果把这些算子拿掉，剩下的大部分模型组织依然能看作 PyTorch 风格的模块装配

### 3. 为什么说它不是重度自定义推理框架

这一节重点不是列举代码，而是给读者一个工程判断标准：

- attention 核心仍然可以落到 `scaled_dot_product_attention`
- 视觉 attention 仍然可以落到 `flash_attn_varlen_func`
- embedding、decoder layer、norm、lm head 这些部分都没有被整套替换

要点是：

- 自定义算子存在
- 但它们主要服务于 MoE 路由和位置编码
- 不是说模型主体脱离了 PyTorch / Transformers 的主干范式

### 4. 为什么它没有 MLA，只有标准 QKV + GQA

这一节是全篇最容易引发共鸣的地方，可以直接回应读者常见困惑。

可以按这个逻辑写：

- 很多人一看到“要做推理优化”，脑子里先想到 MLA
- 但 Wall-X 这里的文本 attention 结构并不是 MLA
- 它仍然是标准 `q_proj / k_proj / v_proj`
- 同时配合 `num_key_value_heads` 和 `repeat_kv` 做 GQA

这里的结论要写得明确：

- 没有 MLA，不代表这个模型“低级”
- 只说明它继承的是 Qwen2.5-VL 这一路的注意力结构
- 你后面做优化，应该围绕它真实存在的结构，而不是围绕一个并不存在的结构

### 5. 文本为什么走 SDPA，视觉为什么走 FlashAttention2

这一节建议从“两个主干”的角度过渡：

- 文本主干是 decoder 栈，当前推理配置走 `sdpa`
- 视觉主干是 Vision Transformer，当前推理配置走 `flash_attention_2`

这里要提前埋一个伏笔：

- 这说明 Wall-X 并不是“所有分支统一用同一种 attention 后端”
- 也说明后面分析性能时，不能只用一个词概括整个模型

### 6. 从优化视角看，真正该先盯哪几条链路

结尾部分建议把文章重新拉回“优化”视角，而不是停在结构结论上。

可以给出一个更实用的优先级：

1. 先搞清楚推理入口和输入张量怎么组织
2. 再搞清楚视觉分支和文本分支怎么合流
3. 再看 decoder 里 MoE 是插在哪一层
4. 最后才去看自定义 CUDA 算子到底占了多少比重

这样结尾后，第二篇就可以自然接到“从推理入口开始看数据加载和模型加载”。

## 可直接使用的开头正文

如果你是从“推理优化”这个目标出发来读 Wall-X 源码，最容易犯的一个错误，就是一上来就钻进 `csrc/ops.cu`，然后把整个项目理解成一个深度依赖自定义 CUDA 算子的模型。

这个判断只对了一小半。

Wall-X 的确有自定义算子，但它们并没有覆盖整套推理主干。更准确地说，Wall-X 里真正下沉到 C++/CUDA 扩展的部分，主要集中在两类问题上：一类是 MoE 相关的 token 重排和 grouped GEMM，另一类是 RoPE 和视觉位置编码相关的索引与 embedding 生成。除此之外，模型的大量主体路径依然沿用的是 PyTorch 和 Transformers 这套常规技术栈。

这个区分很重要。因为如果你没先把这个边界看清楚，后面就很容易在一个错误的问题上越陷越深。比如你会一边翻源码，一边不断问自己：为什么它没有 MLA？为什么它的注意力实现看起来还是常规的 `q_proj`、`k_proj`、`v_proj`？为什么视觉分支又在走 FlashAttention？

这些疑惑本身并不奇怪，问题在于，它们很多都来自一个错误前提：你默认 Wall-X 应该是一套“从注意力到底层算子都被完全重写”的模型。但它其实不是。

更接近事实的说法是：Wall-X 是在 Qwen2.5-VL 这条多模态 decoder 主干上，围绕 MoE 路由、视觉位置编码和动作生成做了定向增强。它有自己的自定义算子，也有自己的动作预测逻辑，但它并没有把基础注意力数学整体换掉。你如果带着“它一定用了 MLA”这样的预设去读代码，就会不断在错误的方向上找答案。

所以真正合理的起点，不是先问某个 kernel 写得快不快，而是先问另一个更基本的问题：Wall-X 的模型结构到底是什么样？文本主干是什么？视觉主干是什么？MoE 到底加在了哪里？动作生成又是接在哪条链上的？

只有把这些问题先回答清楚，后面的性能分析和推理优化才有抓手。否则你看到的只是一些离散的接口名和几个 CUDA 函数名，而不是一条完整的推理路径。

## 第一节正文草稿

### 先别一上来就看 kernel，先看整体结构

从工程角度看，一个模型项目里有没有自定义 CUDA 算子，和“这个模型的核心复杂度在哪里”，并不是一回事。

Wall-X 很适合用来说明这个问题。因为它表面上确实有一层很容易吸引注意力的东西：仓库里有 `csrc/ops.cu`，有 `PYBIND11_MODULE`，有若干导出给 Python 的底层算子。很多人到这里就会很自然地下一个判断：这个项目的主要难点肯定都在自定义 kernel 里。

但如果你顺着调用链继续往上看，就会发现事情不是这样。模型顶层仍然是一个很标准的多模态结构：有视觉编码器，有文本 decoder，有 embedding 替换，有 decoder stack，有 `lm_head`，有 `generate()`。只是其中部分性能敏感路径，被额外下沉成了自定义算子。

这意味着一个很实际的阅读策略变化。对于 Wall-X 这种项目，最有效的理解路径不是“先看 kernel，再反推模型”，而是“先把顶层前向结构看明白，再回头确认哪些局部路径值得下钻”。这样你才能区分：

- 哪些代码是在描述模型主干
- 哪些代码是在描述性能优化
- 哪些代码是在描述 Wall-X 自己新增的任务能力

这三者如果一开始混在一起看，基本一定会乱。

## 第二节过渡草稿

那接下来的问题就很自然了：Wall-X 里到底有哪些自定义算子？它们分别插在什么位置？这些算子的存在，到底意味着模型主体发生了多大程度的变化？

把这个边界讲清楚以后，我们再回头看“为什么它没有 MLA”这个问题，答案就会非常直接。
