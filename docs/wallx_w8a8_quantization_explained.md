# wall-x 的 W8A8 量化到底是什么

这篇文章专门解释 `wall-x` 当前采用的量化路线：**离线权重量化 + 在线动态激活量化** 的 `W8A8`，以及它和 `TensorRT` 全图量化到底有什么本质区别。

如果只看一句话，可以先记住这个结论：

> `wall-x` 当前做的不是“把整个模型编译成一个 INT8 engine”，而是“保留原来的模型执行结构，只把热路径里的 Linear 改成 W8A8 的 INT8 LinearOp”。

这件事听起来像措辞差异，实际上对应的是两套完全不同的工程路线。

---

## 一、先把名字讲清楚：什么叫“离线权重量化 + 在线动态激活量化”

`W8A8` 的字面意思是：

- `W8`：weight 用 8-bit，也就是 `INT8`
- `A8`：activation 也用 8-bit，也就是 `INT8`

但这四个字母不够说明实现方式。真正重要的是：**权重怎么量化，激活又怎么量化。**

在 `wall-x` 这套实现里：

- 权重是 **离线量化**
- 激活是 **在线动态量化**

### 1. 权重离线量化是什么意思

离线的意思是：在真正推理之前，先把原始 `bf16` 权重读出来，算好量化后的 `INT8` 权重和对应的 scale，再单独保存成新的 checkpoint。

当前仓库里，这一步由 `scripts/quantize_w8a8.py` 完成。它会：

1. 遍历 safetensors 权重
2. 判断哪些层应该量化
3. 对选中的 `weight` 做 per-channel 对称 INT8 量化
4. 额外保存 `weight_scale`
5. 如果矩阵尺寸不满足 INT8 kernel 的对齐要求，再额外保存 `weight_orig_shape`

所以量化后的权重文件，不再只是原来的一个 `weight`，而会变成：

- `xxx.weight`：类型变成 `int8`
- `xxx.weight_scale`：每个输出通道一个 scale
- `xxx.weight_orig_shape`：只有 pad 过的层才有

这一步只做一次。推理时不再重复量化权重。

### 2. 激活在线动态量化是什么意思

激活和权重不一样。它不是固定参数，而是每次输入都会变。

所以 `wall-x` 当前没有提前把激活的 scale 固定死，而是在推理时对当前输入现算。做法很直接：

1. 把当前输入 `x` 展平成 `[M, K]`
2. 对每个 token 求一个 `absmax`
3. 用 `absmax / 127` 得到当前 token 的 `act_scale`
4. 再把这个 token 的激活量化成 `INT8`

于是每次真正做 GEMM 时，近似计算的是：

```text
out ~= (x_int8 @ w_int8^T) * act_scale * weight_scale
```

其中：

- `weight_scale` 是离线已经存好的
- `act_scale` 是运行时根据当前输入现算的

这就是“离线权重量化 + 在线动态激活量化”的准确含义。

---

## 二、这和 TensorRT 全图量化到底差在哪

很多人一听“INT8 量化”，脑子里默认想到的是：

- 导出 ONNX
- 喂给 TensorRT
- 校准
- build engine

但 `wall-x` 现在不是这条路。

最容易理解的方式，是把两者看成两个不同层级的优化对象。

### 1. 当前这套 W8A8 是“算子级量化”

它优化的是：

- 某个 `Linear`
- 某组 attention projection
- 某组 vision / MLP / MoE expert projection

也就是说，它替换的是**局部乘法实现**。

模型的整体控制流、数据流、分支、缓存、自定义算子，全都尽量不动。

### 2. TensorRT 全图量化是“图级量化”

它优化的是：

- 整个子图
- 整段执行链
- 多个相邻算子的整体调度和融合

这时候你不再只是“换一个 Linear 的实现”，而是把整段执行系统交给 TensorRT。

### 3. 两者的本质区别

可以直接压成下面这张表：

| 维度 | `wall-x` 当前 W8A8 | TensorRT 全图量化 |
|---|---|---|
| 优化粒度 | 单个 `Linear` / 局部 GEMM | 子图 / 全模型 |
| 权重量化 | 离线脚本自己导出 | TensorRT / QDQ 体系接管 |
| 激活量化 | 运行时动态算 scale | 通常依赖校准或图内固定 scale |
| forward 结构 | 原结构基本保留 | 要导出图并重建执行 |
| 自定义算子 | 原样保留 | 往往需要 plugin |
| 调试方式 | 可逐层对比 | 更黑盒 |
| 性能上限 | 不错，但不是极限 | 更高，前提是图能顺利接管 |

所以这里最重要的一句话不是“都叫 INT8”，而是：

> 一套是在现有执行系统里替换局部算子，另一套是在更高层级上接管整段执行图。

---

## 三、为什么 `wall-x` 更适合前一种，而不是直接上 TensorRT 全图

原因不复杂，核心就是：**`wall-x` 不是一个很适合老老实实导成静态图的模型。**

它现在这条推理链里，有几类 TensorRT / ONNX / `torch.export` 都不太喜欢的东西：

- 自定义 CUDA 算子
- MoE token route / permute / recover
- `asym_dual_gmm` 这类自定义 expert GEMM
- 动态 cache
- ODE / Euler 动作更新链

这意味着如果走 TensorRT 全图量化，你首先要解决的不是“INT8 怎么配”，而是：

- 哪些部分能导出
- 哪些部分要写 plugin
- 哪些分支要拆图
- 哪些动态行为要改写

这就是为什么当前项目选择的是另一条更务实的路线：

> 不改整套 forward，不要求整图静态化，只替换热路径里的 Linear。

从工程视角看，这个决定很合理。因为 `wall-x` 最重的计算本来就集中在大量 GEMM 上。先把最贵的矩阵乘法压进 INT8，往往就已经能拿到一轮非常实在的收益，而不必先重构整套执行系统。

---

## 四、`wall-x` 里到底量化了哪些层，哪些层故意没量化

当前量化脚本的策略不是“看到 Linear 就全量打成 INT8”，而是有明确取舍。

### 1. 优先量化的部分

这条路径里优先覆盖的是热路径上的大头：

- decoder self-attention 的 `q_proj / k_proj / v_proj / o_proj`
- vision attention 的 `qkv / proj`
- 非 MoE 的 MLP 三层 `gate_proj / up_proj / down_proj`
- patch merger 的 MLP

如果开启实验开关，还会继续量化：

- `MoE expert` 里的 `gate_proj / up_proj / down_proj`

### 2. 故意保留 bf16 的部分

以下几类默认不量化：

- `Action Head`
- embedding
- `lm_head`
- normalization
- patch embedding / conv 路径
- 其它不在主热路径、或者量化收益不明显的部分

这里最值得强调的是 `Action Head`。

`Action Head` 没被排除，不是因为它“技术上不能量化”，而是因为它**精度风险更高**。它的输出会更直接地进入动作更新链，包括 `ODE / Euler` 迭代。这里如果引入系统性误差，比主干中间层更容易在多步更新里累计放大。

所以当前工程判断是：

- `MoE expert`：可以试 INT8
- `Action Head`：先保留 `bf16`

这不是教条，而是基于误差传播路径做的优先级排序。

## 五、运行时到底怎么执行：不是“模型变成 INT8”，而是“Linear 变成 INT8”

这一点很关键。

很多人会下意识理解成：“量化之后，整个模型都在 INT8 里跑。”  
对 `wall-x` 这条实现来说，这个理解不准确。

真正发生的事情是：

1. 某些 `Linear` 的权重被换成了 `INT8`
2. 输入激活在进入该 `Linear` 前临时量化成 `INT8`
3. GEMM 用 `INT8 x INT8 -> INT32`
4. 然后立刻反量化回 `bf16`
5. 后面的算子继续按原逻辑运行

也就是说，INT8 主要出现在**矩阵乘法这一小段计算窗口里**。

对 `wall-x` 来说，这种设计有两个现实好处：

- 不会把后面的自定义算子 dtype 路径全打乱
- 可以保证 RoPE、残差、SiLU、MoE route、ODE 这些逻辑尽量保持原状

所以这条路线的关键不是“让所有张量都长时间停留在 INT8”，而是：

> 只让最贵的乘法尽量在 INT8 Tensor Core 上完成，然后尽快回到现有的 bf16 世界。

---

## 六、MoE 是这套量化里最容易误解的地方

如果只看名字，很容易以为：

> “MoE 量化” = “把原来的 MoE 自定义 kernel 改成 INT8”

但 `wall-x` 当前做的并不是这个。

### 1. 原来的 `asym_dual_gmm` 不支持 INT8

`wall-x` 的 MoE expert 原本依赖一个自定义 bf16 双专家 GEMM：`asym_dual_gmm`。

这个 kernel 原本就是按 bf16 路径写的。如果直接把 expert 权重量化成 `INT8`，然后继续按原调用方式喂给它，要么不能跑，要么结果不对。

### 2. 现在采用的是“双路径”

当前真正落地的是：

- bf16 checkpoint：继续走原来的 `dual_gemm`
- INT8 checkpoint：保留 `permute / unpermute / route`
- 但 expert 内部的 `gate / up / down`，改成 per-expert 的 `LinearOp`

换句话说：

- MoE 的路由逻辑没有被改写
- token 重排逻辑没有被改写
- 改的是 expert 内部最重的三段 Linear

这就是为什么前面说：

> `wall-x` 当前不是在做“全图 INT8 化”，而是在做“关键 Linear 的 INT8 化”。

MoE 是这套思路最典型的体现。

## 七、为什么“在线动态激活量化”更容易落地

它最核心的好处是：**不需要预先知道所有输入的激活分布。**

如果激活 scale 是静态的，你一般就得面对这些问题：

- 校准集怎么选
- 文本 token 分布和视觉 token 分布是否一致
- prefill 和 decode 的激活范围是否一致
- 动作 token 和语言 token 的激活分布是否一样

而动态激活量化直接绕开了这些问题。因为它每次都根据当前输入现算 `act_scale`，所以：

- 不需要专门准备校准集
- 输入长度变化时更稳
- token 组成变化时更稳
- 对 `wall-x` 这种多模态、带动作链的模型更省心

这也是它在工程上非常顺手的原因。

---

## 八、为什么它通常又不如 TensorRT 全图量化那么“极致”

前面说它好落地，不代表它没有代价。

它的代价恰恰来自“灵活性”本身。

### 1. 运行时要现算激活 scale

激活 scale 不是预先写死的，而是每次推理都要临时算。  
哪怕这个过程已经做了融合，它仍然是额外工作。

所以一个 INT8 Linear 的实际执行，不只是“做一次 GEMM”，而是至少包含：

- 激活动态量化
- INT8 GEMM
- dequant

### 2. 优化粒度停留在单个 Linear

这条路线最强的地方是“局部替换”，但它的天花板也来自这里。

因为它优化的是单个 `Linear`，所以拿不到太多图级收益，比如：

- 更大范围的算子融合
- 跨层中间张量布局优化
- 整段子图统一调度
- 更激进的 kernel 选择和 memory planning

而这些，正是 TensorRT 更擅长的部分。

### 3. 动态图和自定义控制流仍然保留

这一点对 `wall-x` 是双刃剑。

好处是：

- 自定义算子不用大改
- forward 逻辑不用重构

代价是：

- 这套动态图、自定义路由、MoE 分支带来的边界成本依然存在
- INT8 收益释放得再好，也还是在原系统框架内释放

所以更准确的说法应该是：

> 动态 W8A8 更像是在现有系统里换高效零件；TensorRT 全图量化更像是让另一套擅长 INT8 的执行系统来接管整段传动链。

---

## 九、怎么理解这条路线的价值

如果把这条路线的价值压成几句最实用的话，大概是：

1. 它不是最“学院派”的量化形式，但很适合 `wall-x` 当前的工程形态。
2. 它不要求全模型静态导出，因此能绕开自定义算子和动态图带来的大部分阻力。
3. 它优先打掉的是最贵的 GEMM，所以收益释放路径很直接。
4. 它的性能上限通常低于 TensorRT 全图 INT8，但接入成本也低得多。
5. 对 `wall-x` 来说，这是一条明显更现实、更稳妥的第一阶段量化路线。

---

## 十、一句话收尾

`wall-x` 当前的量化，不是“整个模型都变成了 INT8”，而是：

> **保留原有 C++ / PyTorch 推理结构，只把热路径里的 Linear 换成 W8A8 的 INT8 实现；权重提前离线量化，激活在运行时按输入动态量化。**

这就是它和 TensorRT 全图量化最根本的区别，也是这条路线为什么能在 `wall-x` 里真正落地的原因。
