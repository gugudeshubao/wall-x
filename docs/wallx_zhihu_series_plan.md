# Wall-X 知乎连载拆分方案

## 定位

这套连载建议按 `5 + 1` 的结构来发：

- 前 5 篇是主线，主题是“推理入口、模型结构、MoE 改造、动作生成和优化视角”。
- 第 6 篇是训练番外，主题是“数据构造、标签组织和 loss 设计”。

这样拆的好处是：

- 主线读者可以一直沿着“模型怎么跑起来”这条链看下去，不会被训练细节打断。
- 训练部分的信息密度和阅读心智都不一样，单独成篇更利于理解。
- 每篇都可以独立成文，但前后顺序又能形成系列感。

## 发文顺序

1. 别一上来就谈 CUDA：Wall-X 推理优化前，先搞清楚它到底是什么模型
2. 从 `infer_robochallenge.py` 开始：Wall-X 的推理入口、数据加载和模型加载
3. Wall-X 的视觉主干和文本主干：它不是两套模型，而是一条合流链
4. Wall-X 的 MoE 到底加在了哪里：从 Decoder Layer 到 Token 路由
5. Wall-X 是怎么生成动作的：AR、Flow、KV Cache 和 Euler 积分
6. 番外：Wall-X 是怎么训练出来的？从 `DataCollator` 到双 Loss

## 第 1 篇

### 标题

`别一上来就谈 CUDA：Wall-X 推理优化前，先搞清楚它到底是什么模型`

### 一句话定位

先立判断框架：Wall-X 不是一个“全靠自定义算子堆出来”的模型，除了 MoE 和 RoPE 相关算子，主体依然是 PyTorch 技术栈；如果一开始不先看结构，就会在“为什么没有 MLA”这种问题上反复打转。

### 建议字数

`3500-4500`

### 核心问题

- Wall-X 到底有哪些自定义算子？
- 为什么说它不是重度自定义推理框架？
- 为什么它没有 MLA，只有标准 QKV、GQA、SDPA 和 FlashAttention？
- 真正值得优先优化的路径是什么？

### 目录

1. 为什么推理优化不能一上来就盯 CUDA kernel
2. Wall-X 到底有哪些自定义算子
3. 为什么说它不是重度自定义算子模型
4. 它为什么没有 MLA，只有标准 QKV + GQA
5. 文本为什么走 SDPA，视觉为什么走 FlashAttention2
6. 从优化视角看，真正该先盯哪几条链路

### 文章目标

让读者建立一个基础判断：

- 自定义算子不等于“模型本体完全重写”
- 不搞清结构，优化很容易方向错位
- Wall-X 的主要复杂度在模型组织和 MoE 路由，而不是另起一套注意力数学

## 第 2 篇

### 标题

`从 infer_robochallenge.py 开始：Wall-X 的推理入口、数据加载和模型加载`

### 一句话定位

从脚本入口往下追，把运行时数据如何变成模型输入讲清楚，包括 prompt、图像 token 展开、状态信号注入，以及模型类最终是如何被实例化的。

### 建议字数

`3000-4000`

### 核心问题

- 推理脚本入口是谁在调谁？
- 运行时 observation 如何变成 `input_ids`、`pixel_values` 和其他控制信号？
- `<|image_pad|>`、`<|propri|>`、`<|action|>` 是怎么进入序列的？
- `Qwen2_5_VLMoEForAction` 是怎么加载起来的？

### 目录

1. 入口脚本和模型包装器
2. 运行时输入不是训练样本原样复用
3. prompt 文本怎么构造
4. 图像如何预处理并展开成视觉 token
5. 状态和动作占位符如何进入序列
6. 模型和配置是怎样被加载的

### 文章目标

让读者把“数据加载”和“模型加载”这两件事串起来，知道模型真正接收到的张量是什么，而不是停留在高层接口名上。

## 第 3 篇

### 标题

`Wall-X 的视觉主干和文本主干：它不是两套模型，而是一条合流链`

### 一句话定位

视觉和文本并不是平行跑完再拼接，而是视觉先编码成 embedding，再回填到文本序列里，最后统一送入 decoder。

### 建议字数

`3500-5000`

### 核心问题

- `self.visual` 和 `self.model` 分别负责什么？
- 视觉分支内部做了哪些步骤？
- 文本分支内部还是不是标准 decoder 栈？
- 图像特征是如何替换进文本 token 序列的？

### 目录

1. 顶层模型装配：`self.visual` 和 `self.model`
2. 视觉主干的 forward 路径
3. 文本主干的 decoder 路径
4. 两条分支如何在 embedding 层合流
5. 为什么它本质上还是 decoder 驱动的多模态模型
6. 这条链上的潜在性能热点

### 文章目标

让读者彻底搞清楚视觉分支、文本分支和总前向之间的关系，不再把它理解成“两套模型各跑各的”。

## 第 4 篇

### 标题

`Wall-X 的 MoE 到底加在了哪里：从 Decoder Layer 到 Token 路由`

### 一句话定位

Wall-X 相比基础 Qwen2.5-VL 的最核心增量，不在注意力公式本身，而在 decoder layer 的 MoE 化改造、token type 路由和专家化前向。

### 建议字数

`4000-5500`

### 核心问题

- `Qwen2_5_VLMoEModel` 相对基础模型改了什么？
- `Qwen2_5_VLDecoderLayer_with_MoE` 的执行顺序是什么？
- `TokenTypeRouter`、`SparseMoeBlock` 和 `moe_token_types` 分别干什么？
- `start_indices / end_indices` 为什么存在？
- `JointQwen2VLAttention` 和普通 attention 是什么关系？

### 目录

1. 用 MoE 版本 decoder 替换基础 decoder
2. 每层 decoder 是怎么被改造的
3. token type 如何驱动专家路由
4. `mot_opt` 打开后为什么要做 token 重排
5. joint attention 到底变了什么、没变什么
6. 从工程角度看 MoE 的真实复杂度在哪里

### 文章目标

把 Wall-X 最关键的源码增量讲清楚，让读者知道它的 MoE 改动是“插在哪里、怎么接进去、为什么要这么做”。

## 第 5 篇

### 标题

`Wall-X 是怎么生成动作的：AR、Flow、KV Cache 和 Euler 积分`

### 一句话定位

Wall-X 不只是生成文本，它还要生成动作。这里既有 AR 路径，也有 flow matching 路径，还涉及 cache 截断、prefix prefill 和 ODE/Euler 推进。

### 建议字数

`3500-5000`

### 核心问题

- `model.generate()` 和 `batch_decode()` 的职责差异是什么？
- AR action 和 flow action 分别怎么走？
- `ActionProcessor` 在动作生成里做什么？
- `noisy_action`、`flow`、`v_pred` 的关系是什么？
- 推理时为什么可以做 Euler / ODE 积分？

### 目录

1. 先区分文本生成和动作生成
2. AR action 路径
3. flow action 路径
4. prefix prefill 和 KV cache 截断
5. postfix-only 迭代和 Euler 积分
6. 这条链对推理速度意味着什么

### 文章目标

把 Wall-X 的动作输出逻辑讲透，让读者理解它不是“文本模型后面随便接个头”，而是一套单独设计过的动作预测路径。

## 第 6 篇

### 标题

`番外：Wall-X 是怎么训练出来的？从 DataCollator 到双 Loss`

### 一句话定位

训练链路和推理链路关注点不同，应该单独成篇。这里重点不再是模型结构，而是样本组织、标签对齐、action chunk 构造和损失函数的组合方式。

### 建议字数

`3500-5000`

### 核心问题

- 样本是如何构造成训练 batch 的？
- prompt 和 `labels` 是如何对齐的？
- `action_chunk`、`dof_mask`、`moe_token_types` 是如何生成的？
- 为什么总 loss 会写成 `cross_entropy_loss + flow_loss_weight * flow_loss`？
- 当前训练实现里有哪些值得额外指出的工程问题？

### 目录

1. 为什么训练适合单独成篇
2. 数据加载和 `DataCollator`
3. prompt、占位符和标签对齐
4. flow 目标和动作监督
5. `compute_loss()` 的真实结构
6. 训练实现里当前还不够整齐的部分

### 文章目标

把训练链路从“会调用 trainer”讲到“损失是怎么拼出来的”，让读者看到 Wall-X 的训练部分到底是怎样把文本监督和动作监督绑在一起的。

## 写作建议

- 第 1 篇一定先立一个判断框架，不要急着贴源码。
- 第 2 到第 5 篇都建议按“调用顺序”写，而不是按文件目录写。
- 每篇都保留 1 到 2 个最关键的源码引用点，不要把文章写成逐行 code review。
- 第 6 篇可以明确标成“番外”，避免打断主线节奏。

## 进一步扩写建议

如果后面准备把这 6 篇都真正写成正文，推荐按下面顺序推进：

1. 先把第 1 篇和第 2 篇写完，用来建立整个系列的读者入口。
2. 第 3 篇和第 4 篇是结构核心，可以作为系列中段的主菜。
3. 第 5 篇适合在读者已经理解模型结构后再发。
4. 第 6 篇放在最后做番外，既能补完整体，又不会影响主线阅读节奏。
