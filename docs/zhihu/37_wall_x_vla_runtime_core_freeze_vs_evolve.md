# 37. VLA Runtime 的 core 对象到底哪些该冻结，哪些该继续演化

前面几篇文章里，我其实已经把 `VLA Runtime` 里最核心的一批对象慢慢讲出来了：

- `WorkloadDescriptor`
- `ExecutionPlan`
- `ExecutionReport`
- `PathCapability`
- `Pack/LayoutDescriptor`

同时也一直在强调：

> 这些对象之间必须说同一种语言。

但只要系统真的开始往下长，很快又会遇到一个更微妙的问题：

> 这些 core 对象，哪些现在就应该冻结，哪些反而还不该太早冻结？

这是一个特别容易被处理粗糙的问题。

最常见的两个极端通常是：

### 极端 A

一看到对象重要，就想立刻把它们全部定死。

### 极端 B

担心将来变化太多，于是所有对象都一直保持非常松散。

这两种路最后都容易出问题：

- 全冻结会让系统过早僵化  
- 全开放会让系统语言永远不稳定

所以这篇文章就只讲这个边界：

> `VLA Runtime` 里的 core 对象，到底哪些该先冻结，哪些该继续演化？

## 一、先说结论：应该先冻结“跨层共享的最小语义”，而不是先冻结对象的所有字段

如果把我的判断压缩成一句话，我会说：

> `VLA Runtime` 不应该一上来就把 core 对象的每个字段都冻结下来，而应该先冻结那些会反复穿过 planner、backend、benchmark 和 fallback 的最小共享语义；至于各对象的细节字段和扩展视图，则应该保留一段时间的演化空间。

这里最关键的是两个词：

- 最小共享语义  
- 细节字段

也就是说，我并不主张：

- 所有东西现在都固定

也不主张：

- 所有东西继续自由生长

我更主张的是：

> 先冻结运行时真正赖以沟通的那一小层语言。

## 二、为什么这个问题现在必须回答

因为一旦 runtime 真开始有：

- 多条 path
- 多种 precision
- edge/cloud 分流
- fallback chain
- benchmark 聚合

你很快就会发现：

> 如果 core 对象的最小语义还在飘，系统很难继续收敛。

例如：

- planner 这周理解的 path id，和 benchmark 下周看到的就不一样  
- capability 用的 shape class，report 又另起一套表达  
- pack/layout 的语义一会儿在 backend 里、一会儿在 report 里变换说法

这些问题往往不是因为对象少，而是因为：

> 该冻结的没冻结，不该冻结的又被提前写死了。

所以现在来谈“冻结和演化的边界”，其实恰好是时候。

## 三、先分清楚：runtime 里真正需要冻结的，不是“对象名”，而是“对象承诺”

很多人会天然把“冻结对象”理解成：

> 类名、字段名、目录位置都先定下来。

这通常太表层了。

我更愿意把冻结理解成：

> 这个对象对系统其他层，到底承诺了什么不会随意变。

也就是说，真正该冻结的首先是：

- 语义承诺

而不是：

- 代码表面长得像什么

这一区分非常重要。

因为很多时候：

- 对象的内部组织可以继续演化  
但  
- 它对外的最小语义承诺必须尽快稳定

## 四、哪些东西最该先冻结

如果现在就要在 `VLA Runtime` 里选一批最该先冻结的东西，我会优先选下面这些。

## 五、第一类：path identity 相关语义

例如：

- `Execution Family`
- `Execution Scope`
- 基本 path id 规则

这些东西为什么该先冻结？

因为它们会直接穿过：

- planner
- capability matrix
- report
- benchmark
- fallback

如果这层还不稳定，系统很快就会出现“不同层各说各的 path”的问题。

所以我会非常倾向于：

> 先把 path 这层最小命名语言稳定下来。

## 六、第二类：最小 workload 语义

例如：

- shape class
- deployment mode
- batch 特征
- workload 类别

这些东西不一定要一开始就非常丰富，但它们的最小表达最好尽快稳定。

因为如果连这些都一直在变，后面：

- planner 无法稳定写规则  
- benchmark 也无法稳定聚合

所以：

> workload 的最小分类语言，也属于应该尽早冻结的层。

## 七、第三类：plan / capability / report 之间的对齐点

前一篇文章其实已经把这个问题说出来了。

我现在会更明确一点：

> 那些需要在 `ExecutionPlan`、`PathCapability` 和 `ExecutionReport` 之间反复对齐的字段，应该尽早冻结成稳定语义。

例如：

- path identity
- precision family
- deployment mode
- pack/layout descriptor id
- fallback level

这些字段如果每一层都能自由演化，系统很快就会失去“对象对齐”这件事本身。

## 八、哪些东西不应该太早冻结

为了避免走到“全冻结”的极端，我也想把另一半讲清楚。

## 九、第一类：细粒度 benchmark 视图

例如：

- 某些 stage 的更细拆分  
- 某些特定 kernel 计数  
- 某些调试专用字段

这些东西在 runtime 成长过程中，往往本来就应该保留演化空间。

因为 benchmark 本身就是一个不断学会“该看哪里”的系统。

如果太早把所有细粒度视图冻结，反而会妨碍你继续深入问题。

## 十、第二类：backend 私有扩展字段

比如某个 backend 暂时需要额外暴露：

- 特定 pack 格式元数据  
- graph 命中细节  
- local megakernel debug 信息

这些字段很可能是：

- 某段时间特别重要  
但  
- 还不足以进入 runtime 核心共享语言

这类东西我更倾向于先让它们作为扩展字段存在，而不是过早升格成 core 语义。

## 十一、第三类：局部 path 的具体内部阶段切法

这点也很重要。

比如 `MLP MoE path` 里：

- `down+scatter` 到底算一个阶段还是两个  
- 某种 local megakernel 以后是不是还要再细拆

这些问题在 runtime 早期，其实非常适合继续演化。

更重要的是：

> 不要让这种局部 stage 切法影响全局共享语言的稳定。

换句话说，局部 stage 细节可以继续长，但全局 path identity 不该一起漂。

## 十二、一个更现实的冻结顺序

如果把这件事说得更像工程动作，我更推荐下面这种顺序。

## 十三、第一步：先冻结“跨层共享语义”

包括：

- path family / scope  
- workload 最小分类  
- precision family  
- deployment mode  
- fallback level  
- pack/layout 的最小标识语义

这一步的目标不是让对象复杂，而是让系统先开始说同一种最小语言。

## 十四、第二步：允许对象内部视图继续演化

例如：

- benchmark 视图怎么继续细拆  
- report 里哪些调试字段先出现  
- backend 还需要哪些私有 capability 扩展

这一步的原则应该是：

> 允许演化，但不要污染最小共享语义。

## 十五、第三步：等多模型和多路径开始稳定后，再收第二层字段

这一步通常不该太早。

因为只有在：

- path 更多
- workload 更宽
- benchmark 更成熟

之后，你才更知道哪些第二层字段真的值得升格成 runtime 正式语言。

## 十六、为什么“冻结最小语义”比“冻结对象形态”更重要

我想再单独强调一下这个区别。

因为很多系统在做对象治理时，最容易搞错的就是：

> 先把对象代码结构写得很正式

但 runtime 真正需要的，不是“对象长得像框架”，而是：

> 不同层对这个对象的理解不会反复漂移。

所以如果只能选一件先做，我永远更推荐：

- 先冻结语义  
而不是  
- 先冻结形式

这会让系统的演化空间大很多。

## 十七、我的最终判断

如果把这篇文章压缩成一句话，我想留下的结论是：

> `VLA Runtime` 里的 core 对象，不应该一上来就把全部字段和内部视图都冻结，而应该先冻结那些会反复穿过 planner、backend、benchmark 和 fallback 的最小共享语义；至于细粒度 benchmark 视图、backend 私有扩展和局部 stage 切法，则应该继续保留一段时间的演化空间。

因为对这种系统来说，真正值钱的不是：

> 对象现在看起来有多完整。

而是：

> 它们最关键的那一层语言，是否已经稳定到足以让系统持续收敛，而不是持续漂移。
