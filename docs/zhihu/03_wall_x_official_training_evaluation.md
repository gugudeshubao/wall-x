# 03. 测试 WALL-X 开源具身多模态模型：第三篇，从官方资料看他们是怎么训练和评估的

前两篇已经分别做了两件事：

1. 第一篇，把推理链路在 AutoDL 上真正跑通  
2. 第二篇，把训练链路按当前源码、数据集和模型结构梳理清楚

但如果只停在这两步，其实还缺了一个关键问题：

> `WALL-X` 官方自己到底是怎么训练和评估的？

因为这会直接决定一件事：

> 为什么自己跑出来的实验，只能说明“流程打通了”，还不能说明“已经接近官方模型效果”。

这一篇就专门回答这个问题。

需要提前说明的是，官方目前公开出来的材料主要来自三部分：

- GitHub 仓库 README 与训练文档
- Hugging Face 模型卡
- 论文/白皮书公开摘要

也就是说，能看到的是“训练思路、工程入口、公开结论”，而不是完整的内部训练 recipe。  
因此这一篇更准确的定位是：

> 基于官方公开资料，对其训练与评估路径做一次结构化还原。

## 一、先给结论：为什么自己的实验和官方模型不在一个量级上

如果把最核心的结论先放前面，可以概括成一句话：

> 自己现在这轮实验，验证的是“链路是否成立”；官方 `WALL-OSS` 验证的是“具身基础模型是否成立”。

这两件事不是一个问题。

当前自己的实验特点是：

- 单数据集
- 单卡 `A800 80G`
- 训练预算有限
- 带有适配层修补
- 目标是把训练图跑通、把 loss 跑起来

而从官方公开材料里能看到，`WALL-OSS` 的定位明显更高：

- 大规模多模态预训练
- 多策略训练课程
- 统一的语言、推理、动作框架
- 长时程操作能力评估

所以如果只问“为什么现在训练出来的权重分布和 Hugging Face 上差很多”，答案其实并不神秘：

- 训练数据规模不一样
- 训练目标不一样
- 训练预算不一样
- 评估标准也不一样

## 二、官方把 WALL-X 定位成什么

从官方 README 和模型卡的描述来看，`WALL-X` / `WALL-OSS` 不是一个只面向单任务模仿学习的 policy，而是一个：

> end-to-end embodied foundation model

官方在公开材料里反复强调三个目标：

1. 具身感知下的视觉语言理解  
2. 强语言动作关联  
3. 稳健操作能力

这一点很重要，因为它意味着：

- 官方训练目标不是“把某个数据集 loss 降下来”这么简单
- 它更像是在做一套具身基础模型训练课程

这也是为什么官方材料里会同时出现：

- 多模态预训练
- instruction reasoning
- subgoal decomposition
- fine-grained action synthesis

而不是只给一份“训练数据 = xxx，跑 100 epoch”的说明。

## 三、从仓库能还原出哪些训练层次

虽然官方没有把完整内部配方全部公开，但从 README、模型卡和代码结构，仍然能还原出比较清楚的训练分层。

### 1. 不是从零开始训练，而是站在 VLM 基础上继续做具身建模

仓库训练配置里有两条明显路径：

- 从 `wall-oss` 继续训练
- 从 `Qwen2.5-VL` 继续训练

这说明官方训练思路不是从随机初始化开始，而是：

> 先站在已有 VLM 能力上，再把它往具身空间推。

这和很多具身工作的方法论是吻合的：

- 先要有通用视觉语言能力
- 再逐步建立动作空间和交互能力

### 2. 官方明确有 `FLOW` 和 `FAST` 两条动作分支

仓库和模型卡里都公开了两个模型：

- `WALL-OSS-FLOW`
- `WALL-OSS-FAST`

这至少说明：

- 官方不是只有一条动作建模路径
- 对动作生成，他们自己就做了不同分支的设计与发布

从仓库命名和代码上看，可以把它们粗略理解为：

- `FLOW`：更偏连续动作生成
- `FAST`：更偏动作 token 化和快速动作分支

这件事对训练理解的影响非常大：

> 训练和评估不能只看一个统一 loss，而必须结合动作分支看。

### 3. 训练并不只关心动作，还关心语言与推理结构

论文摘要和模型卡里提到的一个核心概念是：

> Unified Cross-Level CoT

即把下面几层放在统一可微框架里：

- instruction reasoning
- subgoal decomposition
- fine-grained action synthesis

这说明官方训练不是只把“图像 + 状态 -> 动作”当作唯一任务，而是更强调：

- 高层语义理解
- 中层子任务分解
- 低层动作生成

换句话说，动作学习只是其中一层，不是全部。

## 四、官方是怎么组织训练入口的

从仓库公开给用户的入口看，官方对外暴露的是一种偏工程化的 SFT 路径。

最直接的训练入口是：

```bash
bash ./workspace/lerobot_example/run.sh
```

而训练文档里明确强调需要配置这些内容：

- GPU 设置
- 模型路径
- 数据路径
- 机器人 DoF 配置
- 训练超参数

这意味着官方对开源用户开放的是：

> 在他们给定的工程框架里做 supervised fine-tuning

也就是说，公开仓库更偏向：

- 让用户在已有模型基础上继续适配自己的机器人与数据

而不是完整复刻内部所有大规模预训练细节。

## 五、官方模型结构的创新到底在哪里

如果只看仓库名，很多人会下意识把 `WALL-X` 理解成：

> 把 Qwen2.5-VL 拿来，接一个动作头，然后开始训

但从源码看，事情比这个复杂得多。

`wall_x` 并不是原封不动地使用原始 `Qwen2.5-VL`，而是在它上面做了几层很明确的结构扩展。

### 1. 不是直接用原版 decoder，而是换成了 `VLMoE` 版本

在源码里，核心模型不是简单的 `Qwen2_5_VLModel`，而是：

- `Qwen2_5_VLDecoderLayer_with_MoE`
- `Qwen2_5_VLMoEModel`
- `Qwen2_5_VLMoEForAction`

这说明官方不是只在模型最后接一个 head，而是直接改了 decoder layer 的内部结构。

也就是说，具身相关能力并不是“外挂”在最后一层，而是被接进了 Transformer 主干内部。

### 2. `MoE` 不是口号，而是代码里真的有路由和 expert

`wall_x` 里的 `MoE` 主要由这些模块组成：

- `TokenTypeRouter`
- `SparseMoeBlock`
- `BlockSparseMLP`

这些模块在 `vla_mixin.py` 里都能直接看到。

而配置层也明确支持：

- `attention_moe`
- `mlp_moe`
- `norm_moe`

其中从默认配置看，当前更核心的是：

- `mlp_moe = true`
- `attention_moe = false`

这意味着官方当前主要把 `MLP` 这一支改造成了 `MoE`，而不是把整套 attention 全量改掉。

换句话说，`WALL-X` 当前最核心的结构创新之一是：

> 在 Qwen2.5-VL 的语言/视觉主干上，把一部分前馈层改成了专家化结构。

### 3. 这个 `MoE` 不是通用 token MoE，而是和动作 token 绑定的

如果继续往下看，会发现这里的路由不是“随机专家竞争”那种通用做法，而是明显和 token 类型绑定。

训练和推理时，代码里都会构造：

- `moe_token_types`

而这个字段本质上是通过特殊 token 位置来决定的，比如：

- 普通语言 token
- proprioception token
- action token

这意味着它不是简单地对所有 token 一视同仁，而是：

> 让动作相关 token 和普通语言 token 在主干内部走不同专家路径。

这件事对具身任务很关键，因为动作 token 和语言 token 的统计性质并不一样。

### 4. `ActionProcessor` 不是普通 head，而是动作空间适配层

如果说 `MoE` 是主干内部的结构改动，那 `ActionProcessor` 则是具身输入输出被接进模型的关键接口。

它负责的事情包括：

- proprioception 投影
- 动作 chunk 处理
- 动作归一化/反归一化
- flow 分支中的动作隐表示构造

这一层说明官方不是把动作简单看成一个连续向量回归目标，而是显式做了：

- 动作空间建模
- 动作时间建模
- 机器人状态建模

所以更准确地说，`WALL-X` 的创新不只是“加了动作输出”，而是：

> 把机器人动作和状态，以结构化方式接入到 VLM 主干中。

### 5. 为什么这不等于“Qwen 预训练白干了”

这是最容易被误解的一点。

既然 `wall_x` 改了 `Qwen2.5-VL` 的结构，那是不是意味着：

> 原始 Qwen 预训练权重就没意义了？

并不是。

从训练器的 `load_qwen_pretrain_weight()` 可以看得很清楚：

- 原始 Qwen 权重会先被读取出来
- 然后为了适配新的 `MoE` 结构，对应的 `mlp` 权重会被重命名到 `moe.experts.0`
- 最后再加载进新模型结构

这说明官方的思路不是“抛弃 Qwen 底座”，而是：

> 用 Qwen 的预训练主干作为 expert 0 的初始化基础，再把新增的具身结构接上去。

同时，模型加载时还使用了：

- `load_state_dict(..., strict=False)`

这进一步说明：

- 能对上的 Qwen 预训练权重，会尽量保留
- 新增出来的模块，比如动作专家、router、动作处理层，再单独初始化并继续训练

所以更准确的理解应该是：

- 不是“Qwen 预训练白干了”
- 而是“Qwen 预训练成为了具身模型的底座”

这也是很多基础模型改造路线的标准做法：

1. 保留原有通用表征能力  
2. 在此基础上插入任务域结构  
3. 用后续训练把新增结构接到原有表征上

## 六、官方训练里最值得注意的三个设计

从源码结构看，官方训练里最值得关注的不是某一个超参数，而是这三个设计。

### 1. 动作空间不是临时拼进去的，而是被显式建模

`ActionProcessor`、`Normalizer`、`dof_mask`、`agent_pos_mask` 这些模块和字段都说明：

- 动作不是普通回归头顺手接一下
- proprioception 也不是附带输入
- 官方实际上把动作建模当成了架构级设计的一部分

这也是为什么 `WALL-X` 不是“普通 VLM + policy head”的简单组合。

### 2. 训练允许跨 embodiment 的机器人配置

训练配置里存在：

- `customized_dof_config`
- `customized_agent_pos_config`

而模型里也会显式把这些写回 `model_config`。

这说明官方不是把动作空间写死成某一台机器人，而是预留了跨 embodiment 的统一表示接口。

### 3. 训练器本身就支持更大规模分布式优化

从训练器和文档里能看到，官方明确考虑了：

- `Accelerate`
- `FSDP2`
- `torch_compile`

这意味着官方自己设计训练路径的时候，就不是只按单卡调试场景来写的，而是面向更大规模训练组织的。

## 七、官方是怎么评估的

这部分对理解“为什么自己的实验和官方结果差很多”非常关键。

从公开仓库能看到，官方至少有三类评估。

### 1. Fake inference / 基础前向检查

这是最浅的一层：

- 看模型能不能前向
- 看数值是否稳定

这类评估只回答：

> 工程有没有坏

不回答：

> 模型能力到底怎么样

### 2. Open-loop 轨迹对比

仓库里有一个直接的脚本：

- `scripts/draw_openloop_plot.py`

它做的事情很明确：

- 读取测试集
- 生成预测动作序列
- 把预测轨迹和 GT 轨迹画出来

这类评估回答的是：

> 模型在离线动作预测上，与真实轨迹有多接近

这个指标很适合比较：

- 原始模型
- 微调模型

因为它不依赖真实机器人 rollout，复现成本也相对低。

### 3. 环境 rollout / 成功率评估

仓库里还有：

- `scripts/infer_libero.py`

这说明官方并不满足于 open-loop 误差，还会进一步看：

- rollout 成功率
- 长时程任务表现
- 任务级成功率

从脚本逻辑看，评估维度包括：

- task suite
- trials per task
- overall success rate

所以官方的评估思路明显不是只看 loss，而是至少覆盖：

1. 数值稳定性  
2. 离线轨迹质量  
3. rollout 任务成功率

这也是具身模型评估最合理的路线。

## 八、为什么自己的实验和官方结果差很多，是正常的

一旦把官方训练和评估结构捋顺了，就会发现一个很自然的事实：

> 当前自己的实验，根本不在和官方同一个训练预算和评估层级上。

### 自己现在在验证什么

自己当前做的是：

- 单卡 `A800 80G`
- 单数据集 `aloha_mobile_cabinet`
- 训练链路打通
- 1 小时级实验配置

它验证的是：

- 配置是否正确
- 数据是否能对齐
- 模型是否能训练
- loss 是否真的下降

### 官方在验证什么

官方公开材料对应的是：

- 更大规模训练预算
- 多模态预训练基础
- 多策略课程训练
- 多层级任务能力
- rollout 成功率与长时程操作能力

所以这两者天然不在一个比较层级上。

自己现在的实验更像：

> 微调/适配实验

官方公开模型更像：

> 已经完成大规模训练后的基础模型

## 九、如果要公平比较，应该怎么比

最不应该做的比较方式是：

- “自己跑了一轮训练，权重分布不一样，所以训练没意义”

更合理的比较方式应该是：

1. 固定同一数据集  
2. 固定同一评测集  
3. 比 open-loop 误差  
4. 比 rollout 成功率  
5. 比收敛速度和稳定性

也就是说，真正该问的不是：

> 我的模型是不是整体比官方更强？

而是：

> 在当前这个数据分布和任务集合上，这次微调有没有带来可测的收益？

## 十、第三篇该怎么写

如果第三篇要基于“官方是怎么训练和评估的”来展开，最自然的切入点其实不是继续谈训练，而是：

> 为什么推理侧的工程优化，对具身模型同样关键？

因为从前两篇已经可以看到：

- 官方模型本身很大
- 冷启动成本很高
- 真正的评估不只是能不能生成，还包括 rollout 与成功率

这就引出第三篇最自然的问题：

- 推理慢到底慢在哪
- 冷启动怎么优化
- 常驻推理能省多少时间
- benchmark 应该怎么做
- 如果后面做 serving，该关注哪些工程点

也就是说，第三篇最好的方向其实不是“继续重复训练经验”，而是：

> 从官方目标反推，具身模型为什么需要推理加速与服务化视角

## 十一、这一篇的结论

如果只总结一句话，这一篇真正回答的是：

> `WALL-X` 官方不是在做一个单数据集的小型 policy，而是在做一套围绕具身基础模型的训练与评估工程；而自己当前的实验，更多是在这个工程框架里验证训练链路、动作空间适配和最小可复现实验。

所以面对“为什么自己的训练结果和 Hugging Face 模型差很多”这个问题，最合理的答案不是怀疑实验本身，而是先接受一个前提：

> 这两者本来就不处在同一个训练层级。

一旦这一点想清楚，后面的工作就会变得清晰很多：

- 第一篇：确认推理链路成立
- 第二篇：确认训练链路成立
- 第三篇：再讨论推理加速和工程化优化

这才是测试一个具身开源仓库更稳妥的顺序。
