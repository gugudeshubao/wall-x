# 05. 从 Wall-X 到通用 VLA Runtime：第二篇，低精度、MoE 与 megakernel 到底该怎么取舍

上一篇文章里，我把一个判断先立了起来：

> `VLA` 需要一套不同于 `LLM` 的推理优化栈。

如果那篇文章回答的是：

> 为什么这件事值得做？

那这一篇想回答的是另一个更具体的问题：

> 真要开始做 `VLA` 推理加速时，应该先量化、先做 `MoE`，还是先上 `megakernel`？

这是我最近在继续看 `Wall-X` 这类项目时，越来越觉得必须先说清楚的问题。

因为很多讨论一走到这里，就会开始变得非常口号化：

- “量化肯定先做”
- “端侧就应该上 `INT4`”
- “把所有东西揉成一个 `megakernel` 才是终点”

这些说法都不是完全错，但如果不把前提讲清楚，就很容易把路线带偏。

我自己的结论先放前面：

> 对大多数 `VLA` 项目来说，这三件事都值得做，但顺序和边界比“做不做”更重要。

更具体一点就是：

1. 先做对 benchmark 和热区判断  
2. 先把 `MoE / 路由 / layout` 这类胶水热路径打通  
3. 再把低精度能力接进这条 fused 路径  
4. 最后才评估哪些固定场景值得上 `megakernel`

这篇文章就围绕这个顺序展开。

在继续展开之前，我想先把这件事的工程定位说得更明确一点。

从本质上讲，我现在想做的这类工作，其实和 `vLLM`、`llama.cpp` 在各自领域里扮演的角色是类似的，只不过场景更细分。

如果用一句话概括，就是：

> `vLLM` 和 `llama.cpp` 解决的是 `LLM` 的推理系统问题，而这里想补的是 `VLA` 的推理系统问题。

它们的共同点在于，都不是只盯着“某一个算子快不快”，而是在回答更大一层的问题：

- 模型应该怎样运行
- 哪些后端能力必须要有
- 哪些算子值得专门下沉
- 什么样的执行路径最适合目标硬件

但 `VLA` 和 `LLM` 的场景差异也很明显：

- `LLM` 更关注通用文本生成与服务吞吐
- `VLA` 更关注多模态输入、动作输出和低时延控制
- `LLM` 运行时更强调 KV cache、batching 和 token serving
- `VLA` 更强调 router-aware execution、固定 shape、batch=1 和 camera-to-action latency

所以如果要类比，我更愿意把这个方向理解成：

> 不是再造一个 `vLLM` 或 `llama.cpp`，而是在具身场景里补一层“更细分的、面向 `VLA` 的 runtime”。

## 一、为什么这个问题在 VLA 里比在 LLM 里更难回答

如果是普通 `LLM`，很多优化选择已经有相对成熟的工程经验：

- attention 用什么后端
- KV cache 怎么管理
- 量化放在哪一层
- serving runtime 怎么调度

但 `VLA` 的情况不太一样。

它通常同时涉及：

- 图像 token
- 文本 token
- 状态输入
- 动作输出
- expert 路由或分支结构
- 端侧控制和云侧推理两类完全不同的场景

这导致一个现实：

> `VLA` 的性能瓶颈，往往不是单个“大算子”本身，而是多个模块之间的执行链。

也就是说，你在 `LLM` 里习惯的“先盯 attention、再盯 KV cache、最后量化”，不一定能直接照搬到 `VLA`。

这里其实也能看出它和 `vLLM / llama.cpp` 那类工作的边界差异。

如果说 `vLLM` 更像是在解决：

- 怎么把 `LLM` 作为服务更高效地跑起来
- 怎么把上下文管理、KV cache 和调度做对

`llama.cpp` 更像是在解决：

- 怎么把 `LLM` 在更轻量、更受限的硬件环境里跑起来
- 怎么把量化、后端适配和执行路径做薄做稳

那么 `VLA runtime` 真正要解决的问题更接近：

- 怎么把视觉、语言、状态、动作这几种输入输出串成一条稳定低时延链路
- 怎么把 expert 路由、layout 变换和动作分支做成可部署的执行后端
- 怎么在机器人控制约束下，把端侧和云侧的推理路径分开设计

这也是为什么我觉得，`VLA` 方向迟早会需要自己的“runtime 层语言”，而不是永远停留在“训练代码能跑，推理脚本能通”这个阶段。

尤其是在机器人场景里，真正影响系统可用性的往往是：

- camera-to-action latency
- 控制周期抖动
- batch=1 的 steady-state latency
- 固定 shape 下的稳定性
- 中间 layout 变换和 kernel launch 开销

这也是为什么“先量化还是先 `megakernel`”这个问题，在 `VLA` 里必须回答得更细。

## 二、先说结论：不要把量化理解成一个孤立开关

我现在越来越倾向于把量化理解成下面这件事：

> 量化不是一个训练后的小技巧，而是推理后端能力的一部分。

为什么？

因为一旦真正往算子层走，低精度会牵动的不只是权重类型，而是整条执行路径：

- 权重怎么存
- scale 怎么组织
- dequant 在哪里做
- accumulator 用什么精度
- epilogue 能不能融合
- 多个 expert 的 layout 怎么设计
- kernel tile 是不是还合理

所以如果你后面一定会做低精度，那最糟糕的做法通常是：

1. 先做一套和低精度完全无关的高精度执行路径  
2. 最后再试图把 `INT8 / FP8 / INT4` 硬塞进去

这样很容易出现一个问题：

> 前面看起来已经“优化好”的接口和 layout，到了低精度阶段全都不合适了。

但这也不意味着第一刀就应该是“全模型激进量化”。

更现实的理解应该是：

- 量化要尽早进入设计视野
- 但高精度 fused 基线通常还是要先做

这两个判断并不冲突。

## 三、为什么 `MoE` 往往比你想象中更值得优先做

很多人一想到推理加速，会优先去看 attention。

这很自然，因为 attention 是最显眼、也最被讨论的热点。  
但对不少 `VLA` 项目来说，真正更适合作为 first win 的，往往不是 attention，而是 `MoE` 或带 expert 分支的 MLP 路径。

原因主要有四个。

### 1. 结构更规则

典型的 `MoE MLP` 路径通常就是：

- routing
- token permutation
- `gate_proj`
- `up_proj`
- 激活与逐元素乘
- `down_proj`
- weighted accumulation / scatter

这条链路虽然长，但边界清楚。

### 2. 更容易和低精度结合

对低精度来说，最自然的落点通常就是线性层。

而 `MoE MLP` 正好就是一串非常典型的：

- weight-heavy
- layout-sensitive
- 容易做预打包
- 适合 fused epilogue

的算子组合。

相比之下，attention 路径里还混着：

- mask
- rope
- KV cache
- 不同 token 类型之间的额外逻辑

所以第一刀直接砍 attention，未必比先打 `MoE` 更稳。

### 3. 胶水层成本更明显

`MoE` 真正吃亏的地方，通常不只是 GEMM 本身，而是：

- token 排序
- expert 分桶
- 中间结果回写
- 多 expert 间的 scatter/gather

这些恰好是通用框架最不擅长自动优化的地方。

### 4. 对 VLA 特别常见

现在很多 `VLA` 项目虽然不一定公开地把自己叫 `MoE`，但在工程结构上已经很接近：

- token 类型路由
- 动作分支
- 模块化 projection
- 多路径融合

这意味着，即使模型名字不叫 `MoE`，你做出来的很多 expert-aware kernel 仍然有复用价值。

## 四、那为什么不直接先做全模型量化

因为“值得做”和“应该先做”是两回事。

我不建议一上来就做全模型量化，主要有四个原因。

### 1. 你可能还没找准主瓶颈

如果当前最大损耗其实来自：

- `permute / unpermute`
- Python expert loop
- kernel launch overhead
- 中间 buffer 分配

那你先把权重量成 `INT8`，不一定会得到你想要的延迟收益。

### 2. 调试变量太多

一旦从一开始就做全模型低精度，你同时要面对：

- 数值误差
- layout 设计
- kernel 正确性
- 精度回退
- 不同模块之间的接口适配

这会让你很难判断到底是哪一层出了问题。

### 3. VLA 的一些模块并不适合马上量化

比如这些部分，通常更适合先保守一点：

- router
- norm
- 部分 control logic
- action 输出相关路径

这些地方未必是主要带宽瓶颈，但一旦数值不稳，影响会直接体现在动作质量上。

### 4. 低精度最好的落点往往是分阶段推进

更现实的路线通常是：

1. 先做 `BF16/FP16` fused 基线  
2. 先量化最重的线性层或 `MoE MLP`  
3. 再逐渐扩大低精度覆盖范围

这比“一次性全部量下去”可控得多。

## 五、megakernel 到底值不值得做

值，但一定要把它放回正确的位置。

我会把 `megakernel` 理解成一句话：

> 用通用性和可维护性，去交换更低的固定开销和更紧的端到端执行链。

它最有吸引力的地方在于：

- 少 kernel launch
- 少中间 tensor 回写
- 更多寄存器和 shared memory 复用
- 更适合 batch=1、固定 shape、低时延场景

而它的代价同样明显：

- register pressure 更高
- occupancy 可能下降
- shape 一变就容易退化
- 调试更难
- 跨设备移植更难

所以我不赞成把 `megakernel` 当成一种口号。

更合理的提法应该是：

> 先做局部 `megakernel`，而不是一上来做“整层甚至整模型的超级核”。

## 六、什么叫“局部 megakernel”

我更推荐的不是把整条前向都塞进一个巨大的 kernel，而是按真正的热路径边界去做局部合并。

比如下面这些粒度，就很现实：

### 1. `routing + permutation`

如果 token 分桶和排列本身就很重，那么把它们做成一个更紧的执行单元，通常比单独优化其中一个步骤更值。

### 2. `expert projection + layout writeback`

对带 expert 结构的路径来说，这一步经常是“通用框架做得不差，但也绝对谈不上最优”的典型区域。

### 3. `MoE MLP` 的局部整合

像这种链路：

- `gate_proj`
- `up_proj`
- 激活
- elementwise combine
- `down_proj`

就非常适合朝局部 `megakernel` 的方向演化。

### 4. 固定 horizon 的 action decode 路径

如果输出 shape 很稳定，那么 decode/predict 这一段经常也是适合进一步融合的。

一句话说，`megakernel` 最合理的边界不是“模型层级的语义边界”，而是：

> 哪些步骤之间有明显的数据复用、固定 shape 和频繁联动。

## 七、那这三件事到底该怎么排优先级

如果把路线压缩成一张工程表，我会这么排。

### 第一阶段：先找热区，不急着做选择题

要先回答：

- prefill 和 decode 哪个更重
- `MoE` 和 attention 哪个更重
- launch overhead 占多少
- layout transform 占多少
- 端侧和云侧的输入 shape 有多稳定

没有这些数据，讨论“先量化还是先 `megakernel`”基本没有意义。

### 第二阶段：先做高精度 fused 基线

这一步的目标不是最终性能，而是：

- 把算子边界理顺
- 把 layout 确定下来
- 把 workspace 复用机制确定下来
- 把接口变成后面能加低精度的形态

这是后面一切工作的地基。

### 第三阶段：优先打 `MoE / expert-aware` 路径

如果模型里存在明显的 expert 结构，那么这里往往是更现实的 first win：

- 更适合 fused
- 更适合预打包
- 更适合低精度
- 更容易形成通用经验

### 第四阶段：把低精度接进 fused 路径

注意，是“接进 fused 路径”，不是单独做一个低精度旁路。

这一步最关键的是保持一件事：

> 低精度不是额外功能，而是同一条执行路径的后端变体。

### 第五阶段：固定场景再评估局部 megakernel

如果满足这些条件：

- batch 基本恒为 `1`
- 输入 shape 比较固定
- action horizon 稳定
- 服务形态固定
- 已经确认 launch 和中间回写是显著成本

那就可以认真评估 `megakernel` 了。

## 八、云侧和端侧的答案为什么不一样

同样一套模型，在云侧和端侧往往不该走同一套执行策略。

### 云侧更像是：

- 资源更充足
- 通用算子已经很强
- 更容易先从 fused op 和低精度里拿收益
- 更不一定需要极端 `megakernel`

### 端侧更像是：

- batch 很小
- launch 开销占比更高
- shape 更固定
- 更在意 jitter
- 更适合牺牲通用性换低延迟

所以端侧对：

- 局部 `megakernel`
- persistent kernel
- graph capture
- 专用 layout

这些技术的容忍度会更高。

这也是为什么我一直觉得：

> `VLA` 的推理优化，不能只看算子级别，还必须看部署场景。

## 九、对 WALL-X 这类项目，最现实的路线是什么

如果把这件事落回 `Wall-X` 这类项目，我现在更认可的顺序大概是这样：

1. 先把 benchmark 做细  
2. 明确 `MoE`、attention、`permute/unpermute` 的真实占比  
3. 先做一条 `BF16` 的 fused expert 路径  
4. 优先在 `MoE MLP` 或最重的 expert projection 上验证收益  
5. 再把低精度接进去  
6. 最后再看哪些固定场景值得上局部 `megakernel`

这个顺序的重点在于：

> 不要把“低精度”“MoE”“megakernel”当成三条互斥路线，而要把它们看成同一套执行后端逐层深入的三个阶段。

如果再往抽象层提一层，我会觉得这件事和 `vLLM / llama.cpp` 的关系可以这样理解：

- `vLLM` 让大家意识到，`LLM` 不是只有模型，还有运行时
- `llama.cpp` 让大家意识到，`LLM` 不是只能在大服务器上跑，后端和量化本身就是产品能力
- 而 `VLA runtime` 想解决的是：具身模型也不该只有训练代码和 demo，它同样需要自己的运行时、后端和部署方法

只是相比 `LLM`，这里的场景更细分，约束也更重：

- 更强的实时性要求
- 更重的多模态前处理
- 更复杂的 expert / action 路径
- 更明显的 batch=1 特征
- 更强的端侧部署需求

也正因为它更细分，所以它不太可能直接照抄某个通用 `LLM runtime`，而更像是一条独立长出来的分支。

## 十、这一篇真正想得出的结论

如果把这篇文章压缩成一句话，我想留下的结论是：

> 对 `VLA` 来说，正确的问题不是“量化、MoE 和 megakernel 选哪一个”，而是“应该先把哪条 expert-aware 执行路径打通，再把低精度和更激进的执行形态叠上去”。

这也是为什么我越来越觉得，`VLA` 真正缺的不是模型，而是一套完整的推理执行层方法论：

- benchmark 怎么做
- 热区怎么判
- fused 路径怎么定
- 低精度怎么接
- megakernel 什么时候值得做

如果一定要给这个方向找一个大家更容易理解的参照物，那我会说：

> 它在工程角色上有点像 `vLLM / llama.cpp`，但服务的对象不是通用 `LLM`，而是更细分、更强调实时控制的 `VLA`。

如果这套方法能够沉淀下来，那么它的价值就不会只停留在 `Wall-X`，而是会外溢到很多结构相近的具身项目里。

而这，也正是我觉得这条线值得继续做下去的原因。
