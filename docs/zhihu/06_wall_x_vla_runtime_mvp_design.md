# 06. VLA Runtime 的最小可行设计：benchmark、fused op、低精度与局部 megakernel

前两篇文章里，我已经把两个判断立起来了：

1. `VLA` 需要一套不同于 `LLM` 的推理优化栈  
2. 对 `VLA` 来说，`低精度`、`MoE` 和 `megakernel` 都值得做，但顺序比口号更重要

那接下来就该进入一个更具体的问题：

> 如果现在真的要做一个面向具身模型的 `VLA Runtime`，最小可行版本到底应该长什么样？

这里我刻意用了“最小可行”这个词。

因为现在很多讨论一谈到 runtime，就会立刻冲向一个很宏大的目标：

- 支持所有模型
- 支持所有设备
- 支持训练与推理统一
- 支持复杂调度和服务编排

但对 `VLA` 这个方向来说，这样起步通常太重了。

更合理的做法是：

> 先定义一个能真正服务具身推理场景的最小闭环，再决定哪些能力要继续扩。

这篇文章就只做这件事。

## 一、先说结论：VLA Runtime 的 MVP 不该从“通用平台”开始，而该从“可运行闭环”开始

如果把问题说得极端一点，很多系统设计一开始就容易犯同一个错：

> 试图一开始就做成一个通用框架。

这在 `VLA` 方向尤其危险。

因为 `VLA` 本身就比普通 `LLM` 多了很多结构复杂度：

- 图像输入
- 文本输入
- 状态输入
- 动作输出
- token 类型路由
- expert 或分支结构
- 端侧和云侧两种完全不同的部署形态

在这种前提下，如果一上来就追求“支持一切”，结果往往是：

- benchmark 没做好
- 热点没看清
- kernel 边界没定下来
- 接口先膨胀了

所以更现实的路线应该是：

> 先做一个面向单模型、单路径、单设备族的最小可行 runtime。

也就是说，`MVP` 的目标不是“最全”，而是：

- 有明确 benchmark
- 有清楚的热路径
- 有一条可替换的 fused 执行链
- 有一套能落低精度的后端接口
- 有一个能继续承接局部 `megakernel` 的扩展点

如果这五件事能成立，这个 runtime 就已经不是概念，而是真正可迭代的工程基线。

## 二、VLA Runtime 的 MVP 到底要解决什么问题

如果只看模型推理代码，很多人会把 runtime 理解成：

> 把模型 load 进来，然后写一个 `forward()` 调一下。

但真正面向具身场景时，runtime 至少要解决下面四类问题。

### 1. 输入组织问题

`VLA` 的输入不是单一文本，也不是单一图像，而是：

- 图像
- 文本
- 状态
- 可能还带动作历史或额外控制信息

这些输入不仅类型不同，shape 和前处理规则也不同。

所以 runtime 不能只接一个“张量”，而必须明确：

- 哪些输入是固定 shape
- 哪些输入长度可变
- 哪些输入应该尽量提前处理
- 哪些信息会影响 expert 路由和后续 layout

### 2. 执行链问题

`VLA` 的瓶颈往往不在单个大算子，而在执行链：

- token 组织
- `permute / unpermute`
- expert projection
- attention / MLP
- action decode
- 最终输出整理

runtime 要做的不是替代模型逻辑，而是把这条执行链拆清楚，知道：

- 哪些段适合保留框架实现
- 哪些段适合 fused op
- 哪些段适合后面局部 `megakernel`

### 3. 部署目标问题

同一套模型，部署目标可能完全不同：

- 云端 GPU
- 端侧 GPU
- 单卡演示
- 在线机器人控制

这些目标对应的优化优先级完全不同。

所以 runtime 不能假设只有一种执行策略，而应该至少在设计上允许：

- 云侧偏通用 fused 路径
- 端侧偏固定 shape 和低时延路径

### 4. 可度量问题

如果一个 runtime 只能“跑通”，但不能被稳定评估，那它很快就会失去方向。

所以 `MVP` 第一时间就必须有一套像样的 benchmark 和 profiling 体系。

这是我觉得很多项目最容易忽视、但实际上最关键的一层。

## 三、最小可行版本必须先有 benchmark，而不是先有 kernel

我会把这句话写得很明确：

> `VLA Runtime` 的第一组件不是 fused kernel，而是 benchmark。

原因很简单。

如果没有 benchmark，你根本回答不了下面这些问题：

- 当前瓶颈是 prefill 还是 decode
- attention 重，还是 `MoE/MLP` 重
- `permute/unpermute` 占多少
- 图片预处理占多少
- batch=1 的 steady-state latency 到底是多少
- 端侧和云侧的时间构成差异是什么

这一步如果做不好，后面所有的 fused op 和低精度设计都可能是在错方向上努力。

### 1. MVP benchmark 至少要测什么

我觉得最小集合至少包括：

- cold start latency
- warm start latency
- prefill latency
- decode latency
- end-to-end camera-to-action latency
- batch=1 steady-state latency
- 显存占用
- jitter

如果是多路径模型，还应该拆开看：

- 图像预处理
- token 组织
- 主干前向
- 动作输出整理

### 2. benchmark 不是只给论文看，而是给系统设计用

很多人会把 benchmark 看成一种“汇报材料”，但对 runtime 来说，它首先是设计输入。

因为只有先知道时间都花在哪里，你才知道：

- 第一条 fused 路径应该选哪段
- 低精度该优先放在哪层
- `megakernel` 有没有必要

所以 benchmark 不是 runtime 做完以后再补，而是 runtime 的第一组成部分。

## 四、MVP 的第一条 fused 路径应该怎么选

我不建议一上来就去碰“最显眼”的那条路径，而建议先找“最可能形成 first win”的那条路径。

在 `VLA` 里，我会优先考虑两个候选：

### 候选 A：`MLP MoE / expert-aware MLP`

这条路径的特点是：

- 结构规则
- 易于预打包
- 易于和低精度结合
- 前后依赖相对少
- 很适合做 fused activation 和 expert accumulation

如果模型里的 expert 结构比较明显，这条路通常更稳。

### 候选 B：`QKV projection + layout writeback`

这条路径的特点是：

- attention 前的 expert 重排和 projection 很可能是热区
- 能明显减少中间 buffer 和重复 `unpermute`
- 一旦打通，对后续 attention 优化的帮助很大

如果 benchmark 证明这里是瓶颈，那它就适合成为第一条 fused 路径。

### 该怎么选

我更认可的原则是：

> 不要先问“业界通常先做哪个”，而要先问“对当前模型和当前设备，哪条路径最容易拿到稳定正收益”。

这也是 `VLA Runtime` 和通用框架优化最大的差别之一。

它更依赖具体模型和部署目标，而不是抽象地追求“最通用答案”。

## 五、低精度该放在 MVP 的什么位置

这部分最容易被做成两个极端：

- 一个极端是完全不碰低精度
- 另一个极端是一开始就全模型激进量化

我觉得两边都不太对。

更合理的 `MVP` 设计应该是：

### 1. 先把低精度当成后端接口能力预留出来

哪怕第一版 runtime 跑的是 `BF16`，接口层也应该提前考虑：

- 权重预打包怎么定义
- scale 怎么存
- dequant 插在哪层
- accumulator 精度怎么选
- epilogue 有没有融合空间

这样后面接低精度时，不会把接口全部推翻。

### 2. 第一版实现通常还是先跑高精度 fused 基线

这是为了把两个问题拆开：

1. 执行链和 kernel 边界对不对  
2. 低精度数值和数据布局对不对

如果一开始两件事一起做，调试复杂度会很快失控。

### 3. 第一批低精度目标优先选线性层和 `MLP MoE`

原因很直接：

- 更容易预打包
- 更容易评估收益
- 更容易做融合
- 对带宽和存储的帮助更直接

而像 router、norm、部分控制逻辑，则更适合先保守一点。

## 六、局部 megakernel 在 MVP 里应该放在哪里

我不建议把 `megakernel` 当成 `MVP` 第一阶段的必选项。

但我很赞成在设计上给它留出位置。

为什么？

因为对 `VLA` 来说，局部 `megakernel` 是很可能真正有价值的，只是它通常不应该最先上。

### 1. 局部 megakernel 适合解决什么

它最适合的是这种场景：

- batch=1
- 固定或半固定 shape
- 中间张量很多
- kernel launch 开销明显
- 多个步骤之间有强数据复用

这和很多机器人控制场景其实很贴。

### 2. 为什么不是第一步

因为它对你前面的设计要求很高。

只有当下面这些都已经比较清楚时，它才真正值得做：

- 哪段路径是稳定热区
- layout 已经基本确定
- workspace 策略已经明确
- 低精度边界已经大致确定

否则你很容易把一个本来还没定义清楚的执行链，过早固化成一个难以维护的超级核。

### 3. MVP 应该怎样为它预留空间

我觉得最简单的方式就是：

- 先把执行链切成几个明确 stage
- 每个 stage 都有清楚的输入输出 layout
- 允许某个 stage 以后被替换成 fused op 或局部 megakernel

这样你第一版不做 `megakernel`，也不会阻碍后面继续往下演化。

## 七、VLA Runtime MVP 的推荐模块划分

如果让我给一个最小可行设计，我会把它切成五层。

### 第一层：Input Adapter

负责：

- 图像、文本、状态输入整理
- 固定 shape 和动态 shape 区分
- 与模型前处理的边界定义

这一层要解决的是“输入怎么进 runtime”。

### 第二层：Benchmark & Profiler

负责：

- latency 统计
- prefill/decode 拆分
- jitter 统计
- memory 统计
- 热路径 profiling

这一层要解决的是“系统到底慢在哪”。

### 第三层：Execution Planner

负责：

- 选择普通路径还是 fused 路径
- 选择云侧还是端侧配置
- 记录 shape、token 类型、expert 路由相关信息

这一层要解决的是“当前请求该走哪条执行链”。

### 第四层：Kernel Backend

负责：

- 通用高精度路径
- fused op
- 低精度变体
- 后续可替换的局部 megakernel

这一层要解决的是“真正怎么在 GPU 上算”。

### 第五层：Action/Output Adapter

负责：

- 动作输出整理
- 与控制链路的接口衔接
- 端到端 latency 统计回写

这一层要解决的是“结果怎样真正被系统使用”。

如果只看这五层，你会发现它并不夸张。  
它不是一个庞大的平台，而只是把运行时真正需要的职责分清楚了。

## 八、MVP 第一阶段最值得交付的成果是什么

如果这个 runtime 真的开始做，我觉得第一阶段最值得交付的不是“一个很酷的 kernel”，而是这三样东西：

### 1. 一套能稳定复现的 benchmark

这是整个系统的方向盘。

### 2. 一条已经替换成功的 fused 热路径

不管是 `MLP MoE` 还是 `QKV projection`，只要有一条路能稳定证明：

- 接口是对的
- 设计是成立的
- runtime 不是空想

那整个项目就会进入完全不同的阶段。

### 3. 一套为低精度预留好的后端接口

这决定后面能不能平滑地走向真正的部署优化。

## 九、这一套设计为什么和普通模型脚本不是一回事

很多项目一开始都会说：

> 我们已经有推理脚本了。

但“有推理脚本”和“有 runtime”不是一回事。

推理脚本通常解决的是：

- 这次能不能跑
- 这组输入能不能出结果

runtime 解决的是：

- 不同部署目标下应该怎样运行
- 哪条路径该优化
- 后端能力怎样组织
- benchmark 怎样反向驱动系统迭代

这两者的差别，和“能跑起来的 demo”和“能持续迭代的系统”之间的差别，其实是同一件事。

## 十、我对这条路线的最终判断

如果把这篇文章压缩成一句话，我现在更想强调的结论是：

> `VLA Runtime` 的最小可行版本，不该从大而全的平台开始，而该从一套可度量、可替换、可承接低精度和局部 megakernel 的执行闭环开始。

它至少应该具备四样东西：

- benchmark
- 一条 fused 热路径
- 低精度接口
- 局部 megakernel 的扩展位

如果这些都还没有，那讨论“未来 runtime 会不会很强”其实意义不大。

反过来，如果这些已经开始成型，那么即使现在只支持一个模型、一个设备族、一个部署路径，它也已经不是零散优化，而是一层真正开始长出来的 `VLA Runtime`。

而这，才是我觉得这条线值得继续往下做的原因。
