# 28. Wall-X 的 MLP MoE path 到底什么时候值得引入 down+scatter 的联合优化

前面几篇文章里，我已经把 `Wall-X` 的 `MLP MoE` 路径拆成了几个相对清楚的阶段：

- `routing/layout`
- `gate/up`
- `activation + combine`
- `down`
- `scatter/output`

同时也反复强调过一个判断：

> 不要因为前半段已经 fused 了，就自动觉得后半段也应该顺着继续往下焊。

但只要系统继续往下做，你迟早还是会来到一个更细的问题：

> 那么 `down` 和 `scatter` 这两段，到底什么时候值得放到一起做“联合优化”？

这里我刻意用了“联合优化”，而不是一上来就说“直接做 megakernel”。

因为现实里，`down+scatter` 这组边界真正难的地方，不是它能不能合，而是：

> 它是不是已经值得被当成一个联合问题来处理。

这篇文章就只讲这个判断。

## 一、先说结论：`down+scatter` 的联合优化，不该因为它们物理相邻就启动，而该因为它们已经在 benchmark 里共同构成一段高耦合尾巴

如果把我的判断压缩成一句话，我会说：

> `down` 和 `scatter` 是否值得一起优化，不取决于它们是不是在执行链上前后相邻，而取决于它们是否已经在 benchmark 里表现成“一段彼此强耦合、拆开看收益有限、合起来才有意义的尾部成本”。

这个判断里有三个关键词：

- 强耦合
- 拆开收益有限
- 合起来才有意义

少了任何一个，这件事都不一定值得现在做。

为什么我要这么强调？

因为在很多系统里，`down+scatter` 的联合优化很容易被误触发。  
常见理由通常是：

- “`down` 后面就是 scatter，合一下不是很自然吗”
- “前半段都 fused 了，后半段继续顺着做就好了”
- “都已经是 output tail 了，再拆着看是不是太保守”

这些理由都抓到了一点直觉，但它们都还不够。

真正关键的是：

> 这两段是不是已经在数据和成本结构上，开始表现得像一个共同问题。

## 二、为什么 `down+scatter` 会自然成为下一步候选

这件事之所以会被提出来，其实很正常。

因为对 `MLP MoE` 路径来说，一旦前面的：

- `gate/up`
- `activation + combine`

这些部分逐渐收紧，系统的尾部就会越来越显眼。

而 `down+scatter` 恰好处在这样一个位置：

- `down` 仍然属于 compute
- `scatter` 已经开始带上 output 语义
- 两者之间通常没有太多“长期有意义的中间结果”

这就会让人自然想到：

> 既然 `down` 的输出马上就要被 scatter 消化，那中间是不是不值得单独落一遍内存？

这当然是一个很自然的问题。

但自然，不等于立即值得。

## 三、第一种“不值得”联合优化的情况：`down` 还是主要 compute 瓶颈

如果 benchmark 还在告诉你：

- `down` 本身远比 scatter 重
- low-precision 在 `down` 上还有大空间
- 前半段刚做完，后半段占比还没有真正抬起来

那此时过早把 `down+scatter` 视为一个联合问题，通常不是最优选择。

原因很简单。

这时候更值钱的往往仍然是：

> 把 `down` 自己先做对、做稳、做清楚。

如果 `down` 本身还在持续变化，例如：

- 还在试不同 precision
- 还在试不同 packed weight
- 还在试不同 epilogue

那把它过早和 `scatter` 焊在一起，只会把两个问题缠成一个更难调的整体。

## 四、第二种“不值得”联合优化的情况：scatter 语义还没稳定

这一点我认为尤其重要。

`scatter` 这一步表面上看像是一个“尾部写回”，但它经常和系统边界强相关，例如：

- 是否恢复原 token 顺序
- 是否做 weighted accumulation
- 是否直接写成下一阶段所需布局
- output adapter 后面是否还会裁剪、映射、拼装

如果这些问题还没定下来，那么这时候去做 `down+scatter` 联合优化，通常就太早了。

为什么？

因为这会把：

- 还在变化的输出语义
- 还在迭代的 compute 路径

过早锁死成一个更大的实现边界。

这类边界一旦锁早了，后面返工成本会很高。

## 五、第三种“不值得”联合优化的情况：fallback 还不能分层解释

前面几篇文章里已经专门讲过 `fallback`，这里必须继续沿用那个判断。

如果你现在还不能清楚回答：

- `down` 路径失败时退哪里
- `scatter` 路径失败时退哪里
- `down+scatter` 联合路径失败时，是一起退，还是只退一半

那这一步通常还不够成熟。

因为对 runtime 来说，联合优化不只是“把两段合快”，它还意味着：

> 你需要给系统提供一个新的路径层级。

如果这个层级的回退语义不清楚，它很容易把 planner、benchmark 和 backend 全部搞乱。

## 六、什么时候它“值得”被视作联合问题

如果要说正向条件，我更认可下面几条。

## 七、第一条：benchmark 已经表明 `down` 和 `scatter` 是连续尾部成本，而不是两个彼此独立的问题

这里的重点不是“它们都不轻”，而是：

> 它们是否开始表现成一段连续尾巴。

也就是说，benchmark 最好已经能看出：

- `down` 输出之后的回写几乎立刻就被 `scatter` 消耗
- 这中间的中间态本身没有太多独立价值
- 把两段完全拆开看，已经很难继续拿到显著收益

只有这时，把它们当成“联合问题”才更合理。

## 八、第二条：output layout 已经足够稳定

这一条是必须条件。

你至少应该已经比较明确：

- `scatter` 最终写向哪种布局
- weighted accumulation 的语义是否固定
- output adapter 之后还需要做多少额外动作

如果这些还在不断变化，那联合优化几乎一定会过早。

## 九、第三条：memory movement 已经明显比 compute 语义更重要

这通常是 `down+scatter` 之所以值得联合优化的真正原因。

不是因为它们“逻辑上相邻”，而是因为：

> 它们之间的边界正在制造大量不值得的 memory movement。

如果 profiler 已经比较清楚地告诉你：

- `down` 输出中间 buffer 很重
- 这块 buffer 的生命周期极短
- `scatter` 马上又把它读回去

那联合优化的理由就会越来越充分。

## 十、第四条：planner 已经能把它当成一个独立 path 来理解

我会反复强调这一点。

因为任何真正进入 runtime 的联合优化，最后都不只是 kernel 变化，而是：

> 系统里多了一条可选择、可观测、可回退的路径。

如果 planner 还不能表达：

- `down_scatter_joint_path`

这样的概念，那你即使写出来了，也很难让它真正进入系统秩序。

所以我更推荐的节奏通常是：

1. benchmark 先证明它值得
2. planner 先有语言位置
3. backend 再实现它

而不是先偷偷在 backend 里合起来，再让系统其他层慢慢猜。

## 十一、一个更现实的推进顺序

如果现在真的要往这条路走，我更推荐下面这个顺序。

## 十二、阶段一：先把 `down` 和 `scatter` 分开测清楚

不要只看 path total。

你至少要有：

- `down` 自己的 cost
- `scatter` 自己的 cost
- 二者之间的中间 buffer cost

这一步没做好，后面所有联合优化判断都会失真。

## 十三、阶段二：先优化 writeback 形态，而不是先焊 kernel

很多时候，`down+scatter` 真正值得先动的，不是“马上变一个 kernel”，而是：

> 先让 `down` 的输出更接近 `scatter` 真正想消费的布局。

这一步往往就能带来一轮很现实的收益，而且不会过早把边界锁死。

## 十四、阶段三：再评估 weighted accumulation 是否应该一起被拉进来

这里我会更保守一点。

因为 weighted accumulation 一旦被拉进来，通常就意味着：

- output 语义更紧
- fallback 更复杂
- benchmark 解释也更难

所以我更倾向于把它放在 writeback 收紧之后，再单独评估。

## 十五、阶段四：最后才把它定义成真正的“联合 path”

只有当前三步都比较稳之后，我才会建议：

> 把 `down+scatter` 正式提升成 runtime 里的一个独立联合路径对象。

到这个阶段，它才更像是一条真正成立的 path，而不是一个“很想合起来”的实验念头。

## 十六、这件事和局部 megakernel 的关系是什么

从系统演化角度看，我会把 `down+scatter` 联合优化看成：

> 是否值得进入“后半段局部 mega-stage”的前哨判断。

也就是说，它本身还不一定等于 `megakernel`，但它往往是通往那里最现实的一步。

如果这一步都还没成立，那后面直接谈：

- `down + scatter + output adapter`

这种更大的边界，通常只会更早失控。

所以从顺序上说：

> 先判断 `down+scatter` 是否真的构成联合问题，再判断它是否值得进一步长成局部 mega-stage。

## 十七、我的最终判断

如果把这篇文章压缩成一句话，我想留下的结论是：

> `Wall-X` 的 `MLP MoE` 路径里，`down+scatter` 不该因为执行链相邻就自动被联合优化，而应该等到 benchmark 已经证明这两段构成连续尾部成本、output 语义已经稳定、memory movement 成为主要问题、planner 也已经能把它当成独立 path 理解之后，才真正值得作为一个联合优化对象进入 runtime。

因为对 `VLA Runtime` 来说，最重要的从来不是：

> 能不能把更多阶段尽快焊在一起。

而是：

> 哪些边界现在合起来，真的会让系统更快、更稳、更容易解释。
