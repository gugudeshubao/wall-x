# 01. 测试 WALL-X 开源具身多模态模型：第一篇，推理链路与性能实测

最近如果你在看具身智能，大概率会碰到两个很明显的趋势：

1. 机器人模型不再只是传统 imitation learning policy，而是在往更强的多模态基础模型靠  
2. 社区越来越关心一个问题：能不能把视觉、语言、机器人状态和动作统一到同一个模型框架里

`WALL-X` 就是这类方向里的一个典型开源仓库。

这一组文章的目标，不是泛泛介绍具身方向，而是围绕 `WALL-X` 这个开源仓库做一轮相对完整的工程化测试。

系列计划分成三篇：

1. 第一篇：推理链路测试  
2. 第二篇：训练链路测试  
3. 第三篇：推理加速测试

本文是第一篇，重点只放在一件事上：

> 把 `WALL-X` 的推理链路真正跑通，并给出一组可复现的性能数据。

这一组测试在硬件选择上是分阶段进行的：

- 第一篇推理测试：使用 AutoDL 的 `RTX 4090 24GB`
- 第二篇训练测试：计划切到 `A800 80G`
- 第三篇推理加速测试：会基于已经跑通的推理链路继续做优化

如果你的目标是：

- 最近正在看具身智能项目
- 想先理解这个仓库到底在做什么
- 想把推理链路先跑起来
- 再逐步进入训练和推理加速

那么这篇文章更适合作为第一步，而不是直接跳进训练脚本。

这里的硬件路线也值得先说清楚。

之所以把第一篇放在 `4090 24GB`，原因不是它最强，而是它很适合做“推理链路验证”：

- 成本相对更低
- 足够把模型加载、前向、VQA 和 benchmark 跑起来
- 可以尽快验证仓库本身是不是可用

而第二篇训练之所以准备切到 `A800 80G`，是因为训练和推理根本不是一个资源量级的问题：

- 推理更关心模型能不能稳定加载和生成
- 训练更关心显存余量、吞吐和长时间稳定性

所以这三篇文章不是在同一张卡上硬做到底，而是按阶段选择更合适的 GPU。

## 一、为什么这个仓库值得看

对很多人来说，具身项目最难的一点不是“模型够不够大”，而是：

> 它到底是一个 VLM，还是一个 policy，还是一个机器人版的大模型？

`WALL-X` 的有意思之处在于，它不是把这些问题分开做，而是试图把它们放进一个统一框架里。

从仓库 README 的描述可以看出，它服务的是整个 `WALL` 系列开源具身基础模型，覆盖：

- 数据准备
- 模型配置
- 训练
- 推理
- 动作分支
- 评估
- 在线 serving

这意味着它不是一个“只给 checkpoint，不给工程”的仓库，而是一个相对完整的研究到落地中间层。

## 二、WALL-X 这个开源仓库到底在解决什么问题

先把问题说白一点。

如果只做传统机器人 policy，通常输入是：

- 图像
- 状态
- 动作轨迹

如果只做普通 VLM，通常输入是：

- 图像
- 文本

而具身智能真正想做的是：

- 看见环境
- 理解语言
- 结合机器人自身状态
- 最后输出可执行动作

`WALL-X` 就是在做这件事。

从仓库定位上，它更接近一个“具身多模态基础模型工程栈”，核心目标是把以下几类信息统一起来：

- 图像观察
- 语言指令
- 机器人 proprioception
- 动作预测

也正因为如此，它既不是普通图像模型，也不是纯文本大模型，更不是一个只有几百行训练脚本的玩具仓库。

## 三、这个仓库里具体有什么

从代码结构和 README 来看，`WALL-X` 至少包含四块主要能力：

1. 训练  
用 LeRobot 数据和自定义配置训练 `WALL-OSS-FLOW` / `WALL-OSS-FAST`

2. 推理  
包括 fake inference、VQA/COT 推理，以及更接近动作生成的推理路径

3. 动作建模  
仓库里不只是文本生成逻辑，还包含 action head、normalizer、机器人 DoF 配置等动作相关实现

4. Serving  
仓库提供 websocket policy server，可以把模型作为在线策略服务暴露出去

这里有一个非常关键的点：

> 这个仓库不是“只有模型权重”，而是完整保留了训练、推理、动作和服务四条链路。

这也是它作为具身开源项目更值得测试的地方。

## 四、FLOW 和 FAST 是什么

仓库 README 里公开了两个模型分支：

- `WALL-OSS-FLOW`
- `WALL-OSS-FAST`

你可以把它们粗略理解成两种动作建模思路：

- `FLOW` 更偏连续动作生成
- `FAST` 更偏动作 token 化后的快速分支

这次实际下载并测试的是：

- `x-square-robot/wall-oss-flow`

原因也很直接：在系列的第一篇里，先把一条真实推理路径跑通，比一开始就在多个分支之间摇摆更重要。

## 五、这次落地的目标

这次测试的目标非常明确：

- 使用 AutoDL 的 `4090 24GB`
- 下载 `wall-oss-flow`
- 跑通仓库自带的推理脚本
- 验证模型上 GPU
- 给出一组真实 benchmark

一句话结论先放前面：

> `4090 24GB` 可以跑通 WALL-X 推理，但它更适合“推理验证”和“环境打通”；第二篇如果进入训练，硬件会切到 `A800 80G`。

## 六、这次使用的环境

机器配置：

- GPU: `NVIDIA GeForce RTX 4090 24GB`
- 系统: `Ubuntu 22.04`
- CUDA 路径: `/usr/local/cuda`

目录约定：

- 代码目录：`/root/wall-x`
- 虚拟环境：`/root/wall-x/.venv`
- 模型目录：`/root/autodl-tmp/models/wall-oss-flow`

这里有一个非常实际的经验：

- 代码和虚拟环境放系统盘
- 大模型和后续数据集放 `/root/autodl-tmp`

不要把几 GB 乃至几十 GB 的权重直接塞进系统盘，否则很容易把空间打爆。

## 七、为什么这个项目比想象中更难“第一次就跑通”

很多人第一次看 README，会下意识以为：

> 装依赖，下载模型，执行脚本

但 `WALL-X` 实际上是一个组合复杂度很高的项目，它同时涉及：

- Qwen2.5-VL 多模态主干
- 自定义 MoE 路由
- 本地 CUDA 扩展 `wallx_csrc`
- 多种机器人相关输入
- 图文生成和动作建模两套逻辑

也就是说，“推理跑通”至少意味着下面这些环节都没坏：

1. Python 依赖正确  
2. PyTorch 和 CUDA 版本能协同  
3. 本地 CUDA 扩展可以编译  
4. 模型权重可以完整下载  
5. 模型能搬到 GPU  
6. 前向结果没有 `NaN / Inf`

这也是为什么很多时候你卡住的根本原因，不是模型本身，而是环境链条里某一环没有对齐。

## 八、最终整理出来的可用脚本

为了让推理过程具备可复现性，测试时把入口统一整理成了几个明确的脚本。

### 1. 环境脚本

```bash
source scripts/autodl_env.sh
```

它会统一处理：

- 激活 `.venv`
- 设置 `CUDA_HOME`
- 设置 `PATH`
- 设置 `LD_LIBRARY_PATH`
- 设置默认模型路径

### 2. Fake inference 烟雾测试

```bash
bash scripts/run_fake_inference.sh
```

这个脚本不是在做“真实机器人任务”，而是在验证：

- 模型能不能被加载
- CUDA 扩展能不能工作
- 前向图能不能真正跑通
- 输出是否有 `NaN / Inf`

它更像：

> 模型通电自检

### 3. 单次 VQA 示例

```bash
bash scripts/run_vqa_example.sh
```

它会使用仓库自带图片：

```text
assets/cot_example_frame.png
```

然后给出一条自然语言问答结果。

### 4. 常驻式 VQA REPL

```bash
bash scripts/run_vqa_repl.sh
```

这是推理体验最好的入口。

它的特点是：

- 模型只加载一次
- 后续所有问题都复用同一个进程
- 第二问开始，速度会明显比单次脚本更稳定

REPL 支持：

- `:help`
- `:quit`
- `:image /path/to/file.png`
- `:tokens 128`
- `:stats`

### 5. Benchmark 脚本

```bash
bash scripts/run_vqa_benchmark.sh --runs 3 --max-new-tokens 128
```

这个脚本会：

- 先统计模型初始化时间
- 再连续跑多轮相同问题
- 输出每轮耗时和平均值

这个脚本非常适合回答一句经常被问到的话：

> 为什么我感觉模型跑得这么慢？

## 九、实际推理结果

### 1. Fake inference 已跑通

这次在 4090 上，fake inference 的结果包括：

- `Output logits shape: torch.Size([1, 50, 153715])`
- `Output contains NaN: False`
- `Output contains infinity: False`
- 输出 dtype 为 `torch.bfloat16`

这说明最核心的前向图已经跑通，而且数值稳定。

### 2. VQA 已跑通

示例图像问答返回过这样的结果：

```text
To move the red block in the plate with the same color, you should first locate the red block. It's currently positioned on the blue surface, not in the plate. Then, you need to use the plate to pick up the red block. Once you have the red block, you can then place it in the plate with the same color, which is the yellow plate.
```

不讨论回答是否绝对正确，至少说明：

- 模型可以稳定做图文生成
- 不是只会报错、空输出或数值异常

## 十、Benchmark 性能报告

这部分是本文最重要的内容之一，因为它回答的是：

> 在 `4090 24GB` 上，WALL-X 推理到底慢到什么程度？

### 测试条件

- GPU: `RTX 4090 24GB`
- 模型: `x-square-robot/wall-oss-flow`
- 输入图片: `assets/cot_example_frame.png`
- 问题:

```text
To move the red block in the plate with same color, what should you do next? Think step by step.
```

- 生成长度: `max_new_tokens=128`
- 连续运行次数: `3`

### 实测数据

初始化阶段：

| 阶段 | 耗时 |
|---|---:|
| 读取配置 | `0.00008s` |
| 加载 processor | `0.79s` |
| 加载模型并搬到 GPU | `112.31s` |
| 初始化总计 | `113.11s` |

连续三轮推理：

| 轮次 | preprocess | generate | decode | total |
|---|---:|---:|---:|---:|
| Run 1 | `0.043s` | `3.896s` | `0.0003s` | `3.940s` |
| Run 2 | `0.024s` | `3.596s` | `0.0002s` | `3.620s` |
| Run 3 | `0.024s` | `3.689s` | `0.0009s` | `3.715s` |

平均结果：

- 平均生成耗时：`3.73s`
- 平均总耗时：`3.76s`

如果换成更工程化的表述，这组数据其实对应两个不同层面的性能：

### 冷启动性能

- 从进程启动到模型真正 ready，大约 `113s`

这部分主要消耗在：

- 读取权重
- 构建模型
- 搬运到 GPU

### 常驻推理性能

- 模型已经常驻后，单次 VQA 生成约 `3.6s ~ 3.9s`

这部分才更接近真实交互体验。

### 怎么理解这组数字

这组数据可以直接得出两个结论：

1. 真正慢的大头是“首次加载模型”，不是单次生成  
2. 一旦模型常驻，单次 VQA 生成其实已经进入“几秒级”而不是“分钟级”

换句话说：

- 如果你每次都执行一次性脚本，那你体验到的永远是“冷启动”
- 如果你改用 REPL 或服务化推理，后续交互速度会稳定很多

## 十一、为什么你会感觉它还是慢

从体感上说，很多人用 4090 跑完会觉得：

> 这也太慢了

这种体感通常是对的，但根因要分清楚。

慢，主要不是因为 4090 完全不行，而是下面这些因素叠加：

1. 模型很大，单权重文件大约 `8.45GB`
2. 如果每次都新起进程，就要重复加载模型
3. VQA 是自回归生成，不是一次前向就结束
4. 多模态模型的推理链本身就比普通文本模型更重
5. `4090 24GB` 足够推理，但并不宽松

所以一句话总结：

> 真正最慢的不是“4090”，而是“每次都重新加载大模型”

这也是为什么更推荐：

- 用 `run_vqa_repl.sh`
- 或者把它做成常驻服务

而不是反复执行单次脚本。

## 十二、对后续训练的建议

到这一步，推理链路已经清楚了。

如果下一步要做训练，建议顺序是：

1. 先把文件存储挂好  
2. 切到 `A800 80G`  
3. 补训练专用依赖  
4. 再进入训练脚本和数据集准备

这个顺序背后的逻辑很简单：

- 先把推理跑通，建立最小闭环
- 再去追求环境完整性和训练稳定性

对这类大模型项目来说，这比一开始就追求“理论最优环境”更靠谱。

## 十三、最后的结论

如果只总结一句话，可以概括为：

> 如果你最近在看具身智能项目，WALL-X 值得看的地方不只是模型本身，而是它把“多模态理解、动作建模、训练、推理和服务”放进了一个相对完整的开源工程里；而把测试拆成“4090 跑推理、A800 80G 跑训练”的两阶段路线，也更符合真实工程验证的节奏。

对第一次接触这个项目的人来说，最合理的路线永远是：

1. fake inference  
2. 单次 VQA  
3. 常驻 REPL  
4. benchmark  
5. 再进入训练

这也是这次整个落地过程里最有价值的经验。
