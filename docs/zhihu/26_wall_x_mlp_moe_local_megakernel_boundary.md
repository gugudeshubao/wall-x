# 26. Wall-X 的 MLP MoE 从局部 fused 到局部 megakernel 的边界判断

前面几篇文章里，我其实已经把一条很明确的路线慢慢铺出来了：

- 第一条 fused path 很适合先落在 `MLP MoE`
- `MLP MoE` 的接口、数据流、packed weight、low-precision 落点都应该先做清楚
- `scatter/output` 这一段什么时候值得继续 fused，也应该由 benchmark 来推动
- `graph capture` 和局部 `megakernel` 都不该太早引入，而应该是中后期的路径收紧手段

如果顺着这条路线继续往下推，就会自然来到一个更具体的问题：

> 那么 `MLP MoE` 这一段，到底在什么边界上，才值得从“局部 fused path”继续升级成“局部 megakernel”？

这是一个很容易被讲得太玄、也很容易被做得太冲动的问题。

因为只要前面几段路径开始稳定，很多人都会自然产生一个冲动：

> 既然现在已经有 `routing/layout`、`compute`、`scatter/output` 这些阶段了，那是不是该把其中几段合成一个更大的执行单元？

这个方向并不错。  
真正的问题是：

> 哪些边界值得合，哪些边界不该合，什么时候合才值？

这篇文章就只讲这个判断。

## 一、先说结论：局部 megakernel 的边界不该按“语义上顺手”来画，而该按“数据复用 + 固定性 + 可回退性”来画

如果把我对这个问题的判断压缩成一句话，我会说：

> `MLP MoE` 从局部 fused 走向局部 `megakernel` 时，边界不该按模型语义的自然分段来画，而应该按三件事来判断：数据复用是否足够强、输入输出边界是否足够固定、以及失败时是否还能清楚回退。

这三件事缺一不可。

如果只满足其中一两条，通常还不足以让一个局部 mega-stage 真正成立。

为什么我会这么强调？

因为在系统实践里，最常见的误区往往是：

### 误区一：因为“逻辑上很近”，就想把两段合起来

这经常会导致一个结果：

> 合是合了，但实际收益不大，维护成本却明显上升。

### 误区二：因为“前面已经 fused 了”，就自然想继续往后 fused

这会把“技术推进顺序”误当成“系统收益顺序”。

### 误区三：忽略了 fallback 和 benchmark 解释力

结果是后面出现问题时，你根本说不清是：

- 哪段合坏了
- 哪个 workload 不适合
- 还是哪个路径只是没有命中条件

所以我更认可的判断标准，是围绕那三件事展开的：

- 数据复用
- 固定性
- 可回退性

## 二、为什么 MLP MoE 特别容易让人想做局部 megakernel

这件事其实很自然。

因为 `MLP MoE` 的路径本来就很像一条“适合进一步焊接”的局部链：

- `routing/layout`
- `gate/up`
- `activation + combine`
- `down`
- `scatter/output`

它的几个特点都很适合诱发 `megakernel` 直觉：

### 1. 阶段很多，但每段又不至于大到压倒性

这就很容易让人感觉：

> 单段都不够大，合起来应该更值。

### 2. 中间数据有明确的局部流动关系

比如：

- `gate/up` 的结果立刻进入 `activation + combine`
- `down` 的输出立刻进入某种回写路径

这让人天然想进一步减少中间 buffer 和回写。

### 3. batch 常常偏小

尤其在 `VLA` 场景里，batch 小、固定成本显眼，更容易让局部 mega-stage 看起来有吸引力。

所以我一点也不意外大家会想到这条路。  
问题从来不是“为什么想做”，而是：

> 什么时候它真的应该从“想法”变成“实施”。

## 三、局部 megakernel 的第一个判断：数据复用是否足够强

这是我觉得最核心的条件。

如果只是从模型结构看，很多阶段都“看起来很近”。  
但“看起来近”和“值得合成一个 kernel”不是一回事。

真正关键的是：

> 相邻阶段之间，是否存在足够强的数据复用，使得把它们分成两个执行单元会带来明显的中间回写和重读成本？

对 `MLP MoE` 来说，这个问题最先应该落在两组边界上。

## 四、第一组边界：`gate/up` 与 `activation + combine`

这是最自然的一组候选。

因为：

- 输入相同
- 结果立刻被消费
- 中间值本身语义短暂
- 如果单独落内存，通常比较亏

所以在很多系统里，这一组边界往往最早具备“局部 mega-stage”的潜质。

但即使如此，我也不会自动认为它就一定值得。

还要继续问：

- 当前实现里中间值真的有明显回写吗
- benchmark 里这部分 memory movement 是否已经显著
- fuse 之后的调试和 fallback 代价是否还能接受

也就是说，它是最自然的候选，但不是自动成立的答案。

## 五、第二组边界：`down` 与 `scatter/output`

这组边界就更值得谨慎。

原因在于：

- `down` 仍然更偏 compute 语义
- `scatter/output` 已经开始更靠系统布局和后续路径语义

这意味着它们虽然相邻，但未必天然适合很早焊成一个 mega-stage。

我更倾向于认为：

> 这组边界只有在 benchmark 已经明确证明 output writeback 和 weighted accumulation 成为主成本，并且输出语义已经稳定时，才真正值得进入局部 `megakernel` 讨论。

## 六、局部 megakernel 的第二个判断：输入输出边界是否足够固定

这一点经常被低估。

很多人会下意识把“固定 shape”只理解成：

- 张量尺寸是不是固定

但对局部 `megakernel` 来说，真正重要的“固定性”至少有三层。

### 1. 张量 shape 稳定

这是最基础的一层。

如果 shape 变化太大，很多局部 mega-stage 的收益都会迅速下降。

### 2. 路径语义稳定

也就是：

- 这段 path 的输入输出语义是不是已经定了
- 当前是不是还在反复改输出布局
- 当前是不是还在试不同的 output adapter 逻辑

如果语义还不稳定，那你过早合并，后面通常会不断返工。

### 3. runtime 选择条件稳定

也就是 planner 已经比较清楚：

- 哪类 workload 该走这条 path
- 哪类 workload 不该走

如果 planner 对这条路径的适用条件还没稳定，那局部 `megakernel` 也很难真正成为系统路径，而更像是一个难以命中的实验分支。

## 七、局部 megakernel 的第三个判断：fallback 是否足够清楚

这是我觉得最不能省的一条。

如果一个局部 mega-stage 被引入之后，一旦不适合，你说不清楚它该退回哪一级，那它通常还不适合进入主路径。

这里我更倾向于把问题说得非常直接：

> 不能明确 fallback 的局部 `megakernel`，最多适合做研究原型，不适合太早进入 runtime 主路径。

为什么？

因为对 `VLA Runtime` 来说，最可怕的不是某条路径不够快，而是：

- 路径变复杂了
- 解释力掉了
- benchmark 也不再可信

所以如果你想认真判断一段边界是否值得继续向 `megakernel` 推，必须先回答：

- 它失败后退回哪条局部 fused path
- benchmark 怎么记录“命中”与“退回”
- planner 怎么把这件事体面地表达出来

## 八、一个更现实的边界判断顺序

如果现在真的要给 `MLP MoE` 这条路定一个“从局部 fused 到局部 `megakernel`”的现实顺序，我更推荐按下面这个次序来判断。

## 九、第一步：先在 benchmark 里把边界测清楚

也就是：

- `gate/up` 和 `activation + combine` 之间是不是已经有明显中间成本
- `down` 到 `scatter/output` 之间是不是已经有明显 memory movement

如果这一步都看不清，后面所有“合不合”都只能靠感觉。

## 十、第二步：先让路径语义稳定

特别是对后半段来说，要先明确：

- output layout 是否基本确定
- `scatter/output` 的职责是否已经固定
- `fallback` 逻辑是否已经成型

如果这些还没稳，就不太适合进一步收紧边界。

## 十一、第三步：先做最自然的小型合并，而不是一上来就做大的 mega-stage

例如：

- 先把 `gate/up` 和 `activation + combine` 这一组看成候选

而不是一开始就想把：

- `gate/up`
- `activation + combine`
- `down`
- `scatter/output`

全部揉成一个大块。

因为后一种做法通常会把系统解释性快速打碎。

## 十二、第四步：只有当前面的局部合并已经稳定，才继续往后半段推进

也就是说：

- 前半段局部 mega-stage 先站稳
- benchmark 已经清楚表明后半段也成为主成本
- output 语义和 fallback 都成熟

这时后半段才真正值得进入局部 `megakernel` 讨论。

## 十三、为什么这件事和 graph capture 不是同一个问题

有些人会把“graph capture”和“局部 `megakernel`”几乎看成同一类更激进优化手段。  
但对 `MLP MoE` 来说，我觉得它们的边界判断并不一样。

### graph capture 更像是在收紧“整条固定路径”

它最看重的是：

- shape 稳定
- 路径稳定
- launch 开销显著

### 局部 megakernel 更像是在收紧“某几段局部阶段”

它最看重的是：

- 数据复用
- 中间回写冗余
- 阶段边界稳定
- fallback 清楚

所以不要因为两者都“更激进”，就把它们的引入条件混成一套。

## 十四、我的最终判断

如果把这篇文章压缩成一句话，我想留下的结论是：

> `Wall-X` 的 `MLP MoE` 从局部 fused 继续走向局部 `megakernel` 时，边界不该按模型语义顺手来画，而应该按“相邻阶段之间是否真的有足够强的数据复用、输入输出边界是否已经稳定、以及失败时是否还能清楚 fallback”这三件事来判断；通常最先值得认真评估的，是 `gate/up` 到 `activation + combine` 这一组，而不是一开始就把后半段一起焊进去。

因为对 `VLA Runtime` 来说，真正值钱的不是：

> 有一个听起来很猛的局部 `megakernel`。

而是：

> 这块边界为什么现在值得合、合完之后系统还能不能继续被解释、被 benchmark、被回退。
