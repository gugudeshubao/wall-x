# 04. 为什么 VLA 需要一套不同于 LLM 的推理优化栈

> 备选标题：从 Wall-X 到通用 VLA Runtime：具身模型部署层的空白区

前两篇文章里，我分别做了两件事：

1. 把 `WALL-X` 的推理链路真正跑通  
2. 把训练链路、数据集适配和模型结构梳理清楚

到这一步，问题其实已经不再是：

> 这个仓库能不能跑？

而是另一个更现实的问题：

> 如果我没有条件去复现官方级别的大规模训练，下一步最值得投入精力的方向是什么？

我给自己的答案很明确：

> 不是继续硬啃训练，而是转向推理部署和算子级加速。

但这篇文章真正想讨论的，其实已经不只是 `Wall-X` 本身。

更准确地说，我想借 `Wall-X` 这类项目，把一个更大的问题说清楚：

> 为什么今天很多 `VLA` 项目在训练范式上和 `LLM / VLM` 越来越接近，但在部署和推理优化上，却不能简单照搬 `LLM` 的那套方法论？

如果只把这篇文章理解成“给 `Wall-X` 写几个 CUDA kernel 的理由”，那就把问题看小了。  
它真正指向的是另一件事：

> `VLA` 需要一套不同于 `LLM` 的推理优化栈。

这篇文章就围绕这个判断展开。

## 零、先把问题说得更大一点：这不只是 WALL-X 的问题

这两年如果你实际接触过具身项目，会发现一个很普遍的现象：

- 训练侧越来越统一到 `Python + PyTorch + Transformers + 自定义数据/动作管线`
- 模型结构越来越多模态，通常同时接视觉、语言、状态和动作
- 推理部署却明显落后于训练范式的发展速度

也就是说，很多项目已经具备：

- 可训练的代码
- 可下载的 checkpoint
- 可跑通的 demo

但真正一到部署现场，问题马上就会变成：

- 延迟够不够低
- 控制链路稳不稳定
- batch=1 时 GPU 到底有没有吃满
- 端侧和云侧是不是要走两套完全不同的执行路径
- 同一套模型在训练卡上快，不代表在机器人端侧还快

这就是我为什么觉得，这篇文章的标题应该直接提到 `VLA`，而不是只停留在 `Wall-X` 上。

因为 `Wall-X` 不是一个孤例，它更像是这类问题的一个典型样本。

## 一、为什么这件事不能简单照搬 LLM 的推理优化逻辑

`LLM` 这几年已经形成了一整套相对成熟的优化栈：

- attention kernel
- KV cache
- paged attention
- quantization
- serving runtime
- continuous batching

如果只看表面，你很容易觉得：

> `VLA` 不就是多了图像和动作输入吗？那在 `LLM` 的优化栈上稍微扩一层，不就够了？

但实际做下来，问题没有这么简单。

因为 `VLA` 和普通 `LLM` 在推理目标上就有根本差异。

`LLM` 更常见的优化目标是：

- 提升吞吐
- 服务更多请求
- 管理更长上下文
- 提高 token 生成效率

而 `VLA` 在真实机器人系统里，经常更在意的是：

- camera-to-action 的端到端延迟
- 控制周期抖动
- batch=1 时的 steady-state latency
- 固定 shape 下的稳定性
- 多模态输入拼接后的实际执行成本

也就是说，`LLM` 更像是在优化“大规模文本生成服务”，而 `VLA` 更像是在优化“受限硬件上的实时决策链路”。

这两件事不能说完全不同，但重点确实不一样。

所以如果你直接照搬 `LLM` 的那套思路，很容易出现一个问题：

> 你优化了最成熟、最显眼的那部分算子，却没有真正解决 `VLA` 最拖慢系统的那层执行链。

## 二、为什么我不把主线放在“训练出一个接近官方效果的 WALL-X”

这不是因为训练不重要，而是因为要先承认现实。

像 `WALL-X` 这种具身多模态基础模型，官方效果背后通常依赖的是一整套很难低成本复刻的条件：

- 更大的数据规模
- 更长的训练时间
- 更高的显存和更稳定的算力
- 大量训练侧的工程修补和参数经验

如果你只有单卡或者有限的 AutoDL 资源，那么真正可控、可验证、也更容易产出成果的方向，往往不是“追训练效果”，而是：

- 把官方 checkpoint 跑稳
- 把模型服务化
- 把冷启动和单次推理延迟压下去
- 把 GPU 利用率做上去
- 把它变成一个可部署、可复现、可 benchmark 的系统

这个方向的价值并不低。

因为很多时候，模型研究成果是否能进入真实系统，不是卡在“有没有权重”，而是卡在：

- 是否能稳定部署
- 是否能在目标 GPU 上以可接受速度运行
- 是否能在在线服务里保持延迟可控

## 三、为什么 WALL-X 这类项目特别适合做算子优化

很多人一看到仓库里大部分逻辑是 Python 写的，就会自然产生一个判断：

> 这套东西慢，是不是因为它是 Python 实现的？

这个判断只对了一半。

从 `WALL-X` 当前仓库结构看，它当然是一个以 Python 为主的工程，但真正的性能热点并不是“解释器执行几行 Python”本身，而是模型前向里的几类 GPU 热路径：

- 注意力计算
- MoE / MoT 路由
- token 的 `permute / unpermute`
- 多 expert 下的投影层
- 多步推理里的重复显存分配和数据搬运

更关键的是，这个仓库其实已经在告诉你它的优化方向应该往哪里走。

代码里已经有本地 CUDA 扩展：

- `wallx_csrc`
- `csrc/permute.cu`
- `csrc/dual_asym_grouped_gemm.cu`
- `csrc/rope.cu`
- `csrc/rot_pos.cu`
- `csrc/window_index.cu`

这说明什么？

说明这个项目本来就不是把所有性能都押给 PyTorch eager 跑法，而是已经接受了一个前提：

> 这类模型要想跑得更像“工程产品”，就要下探到 C++/CUDA 层，把通用框架不擅长的那部分逻辑收进自定义算子。

也正因为如此，继续沿着这条路做推理优化，是顺着仓库结构往下走，而不是另起炉灶。

## 四、这套模型的瓶颈，未必在你第一眼看到的地方

如果只是普通 LLM，大家第一反应通常是：

- attention 是最大头
- KV cache 是重点
- quantization 是捷径

但 `WALL-X` 这种具身多模态模型没有这么简单。

它比普通 LLM 多出来的复杂度，至少包括：

- 视觉 token
- 文本 token
- 动作 token
- 机器人 proprioception
- 不同 token 类型之间的 expert 路由
- 动作分支和语言分支之间的结构差异

所以它的性能问题往往不只是“大矩阵乘法够不够快”，还包括：

- token 在不同 expert 间来回重排
- 小 batch 下大量碎片化 kernel
- 每层里多次 scatter / gather
- Python 层按 expert 做循环调度

这种场景下，最吃亏的不是单个大 GEMM，而是：

> 一堆本来可以融合掉的中间步骤，被拆成了多个 kernel、多次显存读写和多次 launch。

## 五、从当前代码结构看，哪些地方最值得下刀

这部分不讲空话，只看当前仓库实现。

### 1. 全局 `permute / unpermute`

在主模型前向里，如果启用了 `mot_opt`，token 会先按 expert 重新排列，再进入后续 decoder layer。

这件事本身没有问题，因为 MoT 路由就是这么工作的。  
问题在于，如果你在后续每一层又继续：

- 重排
- 切片
- 投影
- 再恢复原顺序

那整个路径就会充满中间 tensor 和额外显存访问。

所以第一类值得优化的对象不是某个单独 GEMM，而是：

> 能不能让 expert-ordered layout 在更多步骤里保持稳定，少做来回折腾。

### 2. `joint_attention` 里的 expert 循环

当前实现里，一个非常明显的热点是 `joint_attention`。

从代码结构看，它做了几件典型会拖慢推理的事情：

- 按 expert 用 Python 循环分别处理
- 分别计算 `q_proj / k_proj / v_proj`
- 把 Q、K、V 分别写进 buffer
- 再分别做 3 次 `unpermute`

这段逻辑很直观，也容易读，但对 GPU 不够友好。

原因很简单：

- kernel launch 次数多
- 中间读写多
- Q/K/V 三路路径拆得太开
- 小 batch 或短序列时，固定开销占比更高

如果从算子设计角度看，这里最自然的演化方向是：

> 做一个 inference-only 的 fused expert QKV kernel。

更进一步一点，就是把流程改成：

- 输入已经按 expert 排序的 hidden states
- 在同一个 fused op 里完成 expert projection
- 直接产出 attention 所需布局，或者产出 fused QKV
- 尽量把 `unpermute` 次数压到一次

这比单独再去“优化一下某个 Python for 循环”更有价值。

### 3. `o_proj` 路径仍然有重复重排

在 attention 输出后，当前代码里还会再经历一轮面向 expert 的投影和回写。

这意味着什么？

意味着你在前半段已经为 expert 排序付过一轮代价，后半段又要继续付一次。

如果只优化前面的 `q/k/v`，而不处理后面的 `o_proj`，那么收益会被后半段抵消一部分。

所以从实现顺序上看，更合理的是：

1. 先做 `QKV fused`
2. 再做 `o_proj fused`

这样才是完整地把一层 attention 的 expert 路径打通。

### 4. 重复分配临时 buffer

还有一个在推理里经常被低估的问题，是反复创建临时张量。

如果每一层都在做：

- `torch.zeros`
- `torch.empty`
- 中间 buffer 初始化

那么即使算子本身已经不慢，整体端到端延迟仍然会被这类固定损耗抬高。

这类问题在训练里不一定最显著，但在在线推理里会非常明显。  
尤其是机器人控制或者服务化场景，本来 batch 就不大，更容易被 launch 和分配开销拖住。

所以算子优化不能只盯着 GEMM，也要看：

- workspace 能不能复用
- row mapping 能不能缓存
- 固定 shape 下能不能静态分配

### 5. `MLP MoE` 有时比 attention 更适合作为 first win

一提到推理加速，很多人会本能地先盯住 attention。  
但对不少 `VLA` 项目来说，真正更适合作为第一刀的，未必是 attention，而可能是 `MLP MoE`。

原因在于，`MLP MoE` 的结构往往更规则：

- `gate_proj`
- `up_proj`
- 激活与逐元素乘
- `down_proj`
- expert 路由与加权回写

这条路径的几个特点很适合做专用算子：

- 计算边界更清楚
- 前后依赖更少
- 更容易做 `fused SwiGLU`
- 更容易提前做权重预打包
- 也更容易和低精度支持结合

对 `VLA` 来说，这一点尤其重要。  
因为很多模型并不是只有“普通大模型 + 一个动作头”，而是已经带有 expert 分支、token 类型路由或者 action-aware 的 MLP 结构。

在这种情况下，如果你能先把 `MLP MoE` 这条路打通，往往会比一上来就碰 attention 核心更稳，也更容易拿到第一轮正收益。

### 6. 量化不是一个独立开关，而是算子后端能力的一部分

推理优化讨论到后面，一个问题几乎绕不过去：

> 到底要不要量化？

我的判断是：

> 量化要做，但不能把它理解成“最后再打开的一个开关”。

原因很简单。

低精度从来不只是“把权重从 `BF16` 换成 `INT8 / FP8 / INT4`”这么简单，它会直接影响：

- 权重存储格式
- scale 的组织方式
- dequant 的位置
- accumulator 的精度选择
- epilogue 的融合方式
- kernel 的 tile 设计
- 不同 expert 之间的布局和访存策略

换句话说，如果你真的打算做端侧或者低时延部署，那么量化不应该被放在推理优化的最后一步，而应该从一开始就被当成“执行后端能力”的一部分来考虑。

但这不代表第一刀就应该是“全模型激进量化”。

更现实的路线通常是：

- 先把 `BF16/FP16` 的 fused 路径做对
- 再优先量化线性层和 `MLP MoE`
- router、norm、部分控制逻辑先保持在更稳的精度
- 最后再评估是否需要更激进的低比特路线

这比“先全模型量化，再看哪里炸掉”要务实得多。

## 六、为什么我会想到用 CuTe / C++ 来做，而不是继续停留在 Python 层

讲到这里，思路其实已经比较清楚了。

如果你的目标只是“代码更整洁”，那 Python 重构足够了。  
但如果你的目标是：

- 针对特定 GPU 做优化
- 控制 tile shape
- 减少中间显存读写
- 把多个小步骤融合成少数几个大 kernel

那么继续停留在 Python 层基本不够。

这也是为什么我会把方向落到：

- `C++`
- `CUDA`
- `CUTLASS / CuTe`

尤其是 `CuTe`，它的价值不是“让你写得更炫”，而是让你能够更明确地控制：

- thread block 组织
- warp 级切分
- MMA tile 布局
- shared memory 搬运
- 针对 `sm80 / sm89` 这类目标卡做更细的 shape 调优

对 `WALL-X` 这种多 expert、非纯 dense、带重排逻辑的前向路径来说，这种控制力是有意义的。

## 七、但这里有一个很关键的边界：不要想着“把整个模型 C++ 化”

这是我觉得特别需要先说清楚的一点。

如果你因为想做推理加速，就把目标定义成：

> 把整个 `WALL-X` 从 Python 改写成 C++

那大概率会走偏。

原因有三个：

### 1. 大 GEMM 本来就不是最弱的一环

真正的大矩阵乘法，底层已经有非常成熟的实现。  
你自己从零写，不一定能轻松赢过现成库。

### 2. 这套模型真正亏的是“胶水层”

对 `WALL-X` 来说，更难自动优化的是这些部分：

- expert 路由
- `permute / unpermute`
- 多 expert 投影
- 中间 layout 变换

也就是那层介于“模型结构”和“底层 GEMM”之间的胶水逻辑。

### 3. 自定义算子应该先做 inference-only

如果你的目标是推理加速，那最现实的路线应该是：

- 先不做 backward
- 先不兼容所有训练模式
- 先针对固定或半固定输入形状
- 先在单卡目标 GPU 上做出正收益

这条路更窄，但也更容易真正做成。

## 八、从工程 ROI 看，最合理的推进顺序是什么

如果现在就准备进入算子优化，我认为顺序应该是下面这样。

### 第一步：先做对 benchmark，而不是先写 kernel

这一步看起来保守，但实际上决定后面所有工作的方向。

必须先回答下面这些问题：

- 冷启动耗时多少
- prefill 耗时多少
- decode 耗时多少
- 图片预处理占多少
- 哪些 kernel 真正在时间线上最突出

否则很容易出现一个很常见的问题：

> 花很多时间写了一个很酷的 kernel，最后发现它根本不是主瓶颈。

### 第二步：先做 attention backend 的 A/B

当前仓库在推理配置里，视觉分支和语言/动作分支并不是完全同一种 attention 实现。

这说明作者本身已经在做权衡：

- 哪些地方适合 `flash_attention_2`
- 哪些地方先保守走 `sdpa`

所以在自己下场写 kernel 之前，应该先做一次严谨的 A/B：

- 现有实现的端到端延迟
- 不同 attention backend 的差异
- 不同 sequence length 下的拐点

这一步成本不高，但能帮你避免很多无效劳动。

### 第三步：先选最容易拿到 first win 的 expert 热路径

真正开始写自定义算子时，第一目标不应该太大。

更合理的做法是，先在两个候选路径里选一个：

- `MLP MoE`
- `joint_attention` 的 `QKV`

如果当前模型里 `MLP MoE` 开得更重，或者你已经判断低精度会很重要，那么 `MLP MoE` 往往是更好的第一刀。  
如果 attention 路径的重排和 projection 更重，那就先做 `QKV fused`。

关键不在于教条地规定“永远先做哪一个”，而在于：

> 先找那条既是热点、又最容易形成稳定收益的 expert 路径。

### 第四步：在 `BF16` 基线上打通 fused 路径，再考虑低精度

这一步非常重要，因为它决定后面量化是不是会变成一场混乱的补丁战。

更稳的路线通常是：

- 先做 `BF16/FP16` 的 fused 路径
- 先确认 layout、workspace、接口和数值行为都是稳定的
- 再把低精度支持加进去

这样做的好处是，你能把两个问题拆开：

1. 算子边界和执行链是不是设计对了  
2. 低精度数据类型和 dequant/fuse 是不是设计对了

如果这两件事混在一起做，调试成本会迅速失控。

### 第五步：再处理 `o_proj`、layout 融合和更深的 low-precision 路径

当前半段打通之后，再去看：

- `o_proj` 能不能一起融合
- `permute / unpermute` 能不能进一步减少
- 是否能把更多中间结果保留在 expert-ordered layout
- 哪些线性层适合率先切到低精度

这一步做完，才算真正进入“层级别”的 fused optimization。

### 第六步：固定 shape 场景再上 CUDA Graph 或更激进的执行形态

如果后续目标是机器人控制、在线策略服务或者固定 horizon 的 action inference，那么：

- 输入 shape 往往更稳定
- prompt 模板更固定
- 输出长度也更可控

这时候再叠加 `CUDA Graph`，甚至进一步评估更激进的局部 `megakernel`，通常会比开放式 VQA 场景更容易拿到收益。

所以这类技术不是最先做，但很适合作为后续增强项。

## 九、哪些方向我现在不会优先做

为了避免后面路线跑偏，我也把几个“不优先”的方向写清楚。

### 1. 不优先盲目做全模型量化

不是说量化没价值，而是 `WALL-X` 这类模型带有不少自定义模块和动作分支，盲目先做全模型量化很容易遇到：

- 兼容性成本高
- 精度风险不清楚
- 最后发现延迟瓶颈主要不在这里

所以量化要做，但更合理的顺序通常是：

- 先做高精度 fused 基线
- 再优先量化线性层和 `MLP MoE`
- 最后再决定是否扩大到更激进的低比特范围

### 2. 不优先追求训练侧优化

如果主线目标已经从“复现官方训练”切换到了“推理部署和加速”，那训练侧吞吐优化的优先级自然就应该往后排。

### 3. 不优先重写整个 attention kernel

这一点尤其重要。

如果现有路径里已经能复用成熟的 `flash_attention`，那么自己手写一个完全替代 attention kernel 的难度和收益比，通常并不划算。

更值得优化的是框架不擅长自动处理的那部分：

- expert-aware 路由
- 重排
- 分段 projection
- 中间 layout 转换

## 十、这条路线的真正目标，不只是“跑快一点”

最后想把目标再收一收。

对我来说，这条路线真正想得到的，不只是 benchmark 数字好看一点，而是把 `WALL-X` 这样的开源具身模型往“可落地系统”方向推一步。

更具体一点，就是把它变成：

- 可稳定加载
- 可持续运行
- 可 benchmark
- 可服务化
- 可针对目标卡做专项优化

如果这条线走通了，那么你得到的就不只是一个“能跑的开源模型”，而是一套真正有工程价值的具身推理系统。

## 十一、从 WALL-X 再往前走一步，其实就是通用 VLA Runtime

如果只把目前的工作定义成：

> 给 `Wall-X` 做推理加速

那这件事的外延还是偏窄。

但如果把它重新定义成：

> 从 `Wall-X` 这类具身多模态模型出发，抽象出一套面向 `VLA` 的通用推理执行层

那它的价值就会一下子大很多。

这个执行层真正该抽象的，不是训练逻辑，而是推理时的这些共性信息：

- token 类型和分支结构
- expert 数量和路由方式
- 图像、文本、状态、动作的拼接规则
- action horizon
- 常见输入 shape 范围
- 哪些场景是固定 shape
- 哪些路径更适合端侧，哪些更适合云侧

一旦这些信息能被显式描述出来，你就不再只是写几个散落的优化 patch，而是在形成一层新的 runtime 抽象：

1. 上层保留 `Python` 训练和模型定义  
2. 中间层输出面向推理的结构化描述  
3. 下层根据设备选择专用执行后端

到这里，问题就从：

- “这一个模型怎么加速”

变成了：

- “这一类 `VLA` 模型应该怎么部署”

这就是为什么我觉得第二个备选标题也成立：

> 从 Wall-X 到通用 VLA Runtime：具身模型部署层的空白区

因为今天真正缺的，往往不是模型本身，而是这层部署方法。

## 十二、这一篇之后，我接下来会做什么

如果继续按这个方向推进，下一阶段最合理的工作顺序会是：

1. 先补一套更精确的 profiler 和 benchmark  
2. 确认 `joint_attention`、`MLP MoE`、`permute/unpermute` 和 expert projection 的真实耗时占比  
3. 先在一条 expert 热路径上做 `BF16` fused 版本  
4. 用 `C++/CUDA` 接进现有 `wallx_csrc`  
5. 再把低精度支持和权重预打包加进去  
6. 最后再根据目标 GPU 做 tile、graph 和更激进执行形态的调优

一句话总结这篇文章的结论：

> 对当前这套 `WALL-X` 工程来说，最值得做的推理加速，不是把 Python 统统推翻重写，也不是一上来就全模型量化，而是围绕 MoT 路由、`permute/unpermute`、`MLP MoE` 和 expert projection 这些真正的热路径，先做面向目标 GPU 的 fused 执行路径，再把低精度能力纳入后端设计。

这件事的门槛不低，但方向是对的。

而且一旦做成，产出的价值会比“勉强跑一轮训练”更扎实。
